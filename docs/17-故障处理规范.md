# 17 - 故障处理规范

## 故障分级

| 级别 | 定义 | 示例 |
|---|---|---|
| P0 | 服务整体不可用 | 数据库挂了、后端崩溃、电脑关机 |
| P1 | 核心功能不可用 | 无法下单、无法接单 |
| P2 | 局部功能异常 | 上传失败、消息延迟 |
| P3 | 体验问题 | 页面卡顿、样式错乱 |

## 标准排查顺序

1. `npm run infra:status` 一键体检（容器健康/后端端口/穿透状态）
2. 看后端日志（异常堆栈、requestId）与容器日志
3. 数据库连通性检查（/api/v1/health 返回各服务状态）
4. 网络检查（Tunnel 状态、本地端口监听）
5. 定位原因 → 修复 → 测试 → 记录到当日开发日志（原因/处理/预防措施）

## 常见故障速查

| 现象 | 原因 | 处理 |
|---|---|---|
| 后端起不来 | 端口占用 / .env 缺失或错误 / 数据库未启动 | 查端口、Joi 报错、infra:start |
| 接口 500 | 代码异常 | 日志中按 requestId 定位堆栈 |
| 数据库连不上 | 容器未启动/健康检查失败/密码错误 | docker ps、health 日志、infra/.env |
| 外网连不上 | cloudflared 未运行/电脑断网/后端未监听 0.0.0.0 | status.ps1、重启服务 |
| 手机连不上本地后端 | 不在同一局域网/防火墙 | 开发期用 Tunnel 或局域网 IP + 防火墙放行 |

## 恢复验证

任何修复完成后：先自测故障场景恢复 → 再跑受影响的正常流程 → 记录验证结果。

## 未解决问题登记

暂未解决的故障必须写入当日开发日志"未解决的问题"，并注明临时规避方案与计划解决阶段。
