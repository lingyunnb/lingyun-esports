# 02 - 数据库设计（权威文档，与 migration 同步维护）

## 通用约定

- 引擎 InnoDB，字符集 utf8mb4 / utf8mb4_unicode_ci；主键 `id BIGINT UNSIGNED AUTO_INCREMENT`
- 每表 `created_at` / `updated_at DATETIME(3)`；时间统一存 UTC（TypeORM timezone 'Z'）
- 积分金额字段 `DECIMAL`（2026-09-23 起支持小数，如 5.5 积分/局）：
  - 商品价/订单快照/结算 = DECIMAL(12,2)；钱包余额/流水/等级累计消费/榜单金额 = DECIMAL(14,2)
  - 发放积分仍建议整数；结算 70/30 四舍五入到 0.01
- 所有对外编号（订单号/流水号/消息ID/幂等键/用户ID/工号）均建唯一约束，防重放
- 逻辑删除优先用 status 字段，不物理删除关键业务数据
- 表结构变更必须走 migration（禁 synchronize，见 docs/10）

任意时刻：`SUM(wallet.balance) == SUM(全部 grant) - SUM(全部 recover) + SUM(全部 order_refund) - SUM(全部 order_pay)`（含被禁用账号）。并发脚本与定期对账均按此断言（详见 docs/06）。

#### 为什么用「生成列 + 唯一键」而不是普通唯一键（**必读，改这张表前先看这段**）

需求是两条**互相冲突**的约束：① 同一 boss 在 active 时最多 N 条（**N 默认 1、且可配**）；② 同一打手同时只能被一个老板绑定。
MySQL **没有条件唯一索引（无 partial index）**，固定唯一键无法同时表达"上限可配"与"解绑后释放名额"。做法：

- 两个生成列在 `status≠active` 时**为 NULL** → **MySQL 唯一索引忽略含 NULL 的键**（多行 NULL 互不冲突）；
- `UK_wib_active_worker`：**一个打手账号同时只能被一个老板绑定** —— 与上限无关的**语义硬约束**（否则一个打手会被多人来回切换，语义混乱）；解绑后该列变 NULL，名额立即释放；
- `UK_wib_active_boss_slot`：第 i 条 active 绑定占槽位 i → 上限 N 时最多 N 条；**上限改成 2/3 也成立**（这是普通唯一键做不到的）；
- **并发**：服务层"计数 + 取最小空闲槽"之外，**唯一键是最终真相**（DB 级实测：同 boss 第二条 active → `ERROR 1062 ... UK_wib_active_boss_slot`；同 worker 第二个 boss → `ERROR 1062 ... UK_wib_active_worker`）；
- 唯一键报错在服务层翻译为中文 400，**不把 1062 泄露给客户端**。

| created_at / updated_at | DATETIME(3) | 通用约定 |

索引 / 约束：

- `UNIQUE UK_rqr_wallet_txn (wallet_transaction_id)` —— **一笔流水只能对应一张申请**（幂等的数据库级兜底）。
  MySQL 唯一索引忽略 NULL → 未发放的申请（NULL）互不冲突，天然支持"多张待审"。
- `IDX_rqr_user_status (user_id, status, id)` —— 老板端"我的申请"列表 + **待审核数上限**统计
  （`WHERE user_id=? AND status='pending'`）都命中它，高频路径不扫全表。
- `IDX_rqr_status (status, id)` —— 管理端/受限会话的待审列表分页。

#### 幂等：一张申请只能发放一次（三层，缺一不可）

1. **事务 + 行锁**：`SELECT ... FROM recharge_request WHERE id=? FOR UPDATE`，拿到锁后校验 `status='pending'`；
   并发两个 grant 被串行化，后者看到 `granted` → 中文 400「该申请已发放」；
2. **条件 UPDATE 判 affectedRows**：`UPDATE ... WHERE id=? AND status='pending'`，`affectedRows !== 1` → 抛错整体回滚 + 中文 400；
3. **唯一约束兜底**：`wallet_transaction.idempotency_key = 'recharge:' + requestId`（唯一）+ 本表 `UK_rqr_wallet_txn` ——
   即便前两层被绕过，数据库也不允许重复加分。

**发放走的是既有超管发积分能力**（`WalletService.grantInTx()` → 同一个 `executeChange`）：
事务内行锁钱包 → 改余额 → 写流水（含 `balance_before/after` 快照）→ 幂等键唯一约束兜底。
**没有第二套积分逻辑**（docs/06 铁律）。

#### 为什么配置落 `system_setting` 而不是单开 `recharge_config` 表（负责人给了两选项，**这里说明取舍**）

选 `system_setting.recharge_config`，**唯一决定性理由**：只有它才能真正"复用 `is_high_security` 机制"。

- "仅超管可写"这套机制**本身就是 `system_setting` 行的属性**（`is_high_security=1` +
  `SystemSettingService.update()` 里的 `actorRoleCode !== 'super_admin'` 判定）。
  单开一张表就得把这条规则**再实现一遍**（另写一个"查角色码 → 比 super_admin"的分支）——
  与 docs/04 反复强调的"同一规则只有一份实现"直接冲突（安全审计 F1 的同一类根因）。
- 单行 JSON 的读写与既有 `platform_commission_rate` / `purchase_points_hint` / `worker_binding_max_per_boss`
  **完全同一套**：管理端「系统设置」页无需新增页面就能看到并编辑；写入口唯一
  （`SystemSettingService.update` → `validate` 按 key 调 `assertRechargeConfig`）。
- 读侧成本等价：`setting_key` 唯一索引 → 主键级单行读（实测约 2ms），且**不缓存**。
- 代价（已知并接受）：`cfg_value` 是 JSON，DB 层不能给单个字段加类型约束 →
  由 `modules/recharge/recharge-config.ts` 的 `parseRechargeConfig`（读侧按字段回退）与
  `assertRechargeConfig`（写侧中文 400）两处把关，与 `parseWorkerBindingMax` / `parseCommissionRate` 同口径。

**表结构部分仍按负责人给定口径建真表**（`recharge_qr_code` / `recharge_request` / `recharge_admin`）——
它们是业务数据（要分页、要唯一约束、要行锁、要审计），不是配置。

| `remark` | varchar(200) NULL | 评价内容（可选；trim 后空串按未填处理 = NULL） |
| `hidden` | tinyint(1) | 0 正常 / 1 已隐藏（仅 `review:moderate` 可改；`hidden=1` 公开接口一律不下发） |
| `hidden_reason` | varchar(200) NULL | 隐藏原因（隐藏时必填；**恢复可见时清空** —— 语义是"当前的隐藏原因"，历史原因在 `operation_log`） |
| `created_at` | datetime(3) | 评价时间（服务层显式写入，便于同事务回显） |

索引：`UK_review_order (order_id)` · `IDX_review_worker (worker_id, hidden, created_at)`
（公开打手页的两个查询——好评率聚合与最近 N 条——都走这一条）。

**不做的事**（刻意，避免"第二条真相"）：
- **不在本表/`worker_stats` 存"好评率"**：公开接口**实时聚合**本表（`COUNT/SUM … WHERE worker_id=? AND hidden=0`）。
  冗余列要在"评价写入 / 隐藏 / 恢复 / 删号"每条路径上同步维护，漏一处就是永久偏差
  （与 CLAUDE.md「退款时战绩与钱包必须同步回退」同类风险）。
- **不落售后单**：差评只回 `needAfterSale=true`，客户端引导走**既有的** `POST /user/orders/:id/appeal`
  （唯一售后入口，一单一申诉），订单状态也**不改**。
- **不做"超时未评价/放弃评价"的状态机**：竞品有 `"未及时评价，评价已超时～"`，
  我们第一阶段只做"完成了就能评"，不引入定时任务与新的状态位（少一条真相、少一个定时器）。

### 新表 `user_game_account` — 老板保存过的游戏账号（同一游戏一行）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | bigint unsigned PK | |
| `user_id` | bigint unsigned **UK(部分)** | 老板账号（只来自 JWT sub） |
| `game_id` | bigint unsigned **UK(部分)** | 游戏（`game.id`） |
| `game_player_id` | varchar(64) | 游戏 ID（与 `order.game_player_id` **同长度同校验正则**） |
| `game_zone` | varchar(32) NULL | 游戏分区（比 `order.game_zone`(16) 宽：这是用户自己的备忘，不为旧枚举收紧） |
| `updated_at` | datetime(3) | 最近一次使用/保存（下单自动 upsert 与手工保存都会前进） |

唯一键 `UK_uga_user_game (user_id, game_id)`；**无 `created_at`**（本表回答"我现在用哪个号"，
不回答"第一次什么时候填的"）。

写入只有两条路径，且**共用同一个 `GameAccountService.upsert()`**：
1. **下单成功时服务端自动 upsert**（`OrderService.createOrder` → `rememberGameAccountBestEffort`，
   在**事务提交之后**，best-effort：失败只告警，绝不影响下单成功）；
2. `POST /user/game-accounts`（用户手工保存/改号）。

→ 因此**客户端不需要调 POST 来"保存"**，只调 `GET /user/game-accounts` 做回填。

### 其它表 / 权限的改动

- `permission` 新增 **1 个专用窄权限点**（migration `1814000000000`，**只授予 `super_admin`**）：
  | code | name | group |
  |---|---|---|
  | `review:moderate` | 评价治理（查看/隐藏/恢复） | 评价 |

  与 `recharge:review` / `withdraw:review` **完全同口径**（不复用任何 `admin:*` 大权限）。
  该点**同时覆盖读与写**（列表 + 隐藏/恢复）：评价原文是用户生成内容，"看列表"与"改可见性"
  是同一个人在同一张列表上的连贯动作（拆出一个只读点只会产出"能看不能改"的空壳授权）。
- **其余表一行未动**：`worker_stats` 没加列、`order` 没加列、`media` 用途没加（评价不涉及图片）、
  `system_setting` 没加配置行（评价无可配项）。
