# 12 - 测试规范

## 原则

- **未运行不得说测试通过；未检查不得说没有 Bug**
- 每个核心功能至少覆盖：正常流程 / 异常流程 / 空数据 / 错误参数 / 重复点击 / 并发 / 断网与恢复 / 权限不足 / 非法权限 / 数据不存在 / 数据被修改 / 接口超时 / 服务器异常 / Token 过期 / WebSocket 断开 / 客户端异常退出
- 重点模块（积分、订单、权限、客服、聊天、商品价格）必须逐条过

## 测试层次

| 层次 | 工具/方式 | 时机 |
|---|---|---|
| 编译/静态 | tsc、vue-tsc、flutter analyze | 每次改动 |
| 接口自测 | curl/Swagger + 真实数据库 | 每个接口完成时 |
| 并发脚本 | 一次性 Node 脚本（scripts/tmp/） | M4/M5 下单、抢单、发放 |
| 越权用例 | docs/09 安全自测清单 | 每个新模块 |
| 联调回归 | 真机/模拟器 + 浏览器 + 后端 | 每个里程碑末 |
| 全链路 | 外网三端 | M9 |

## 并发测试标准脚本（每次核心并发场景必跑）

- 同幂等键 50 并发下单 → 断言：仅 1 个订单、扣款 1 次、余额正确
- 20 并发抢同一单 → 断言：仅 1 个 worker 成功、状态日志唯一
- 并发发放积分 → 断言：流水数与余额之和守恒（docs/06 公式）

## 每里程碑验收固定动作

1. 运行三端 + 后端
2. 按里程碑验证标准逐条自测（正常 + 异常）
3. 查数据库（数据落库正确）、查日志（无异常堆栈）
4. 回归上一里程碑功能（确认未破坏）
5. 结果写入当日开发日志

## 自动化测试范围（按需，不追求覆盖率指标）

- server：核心服务单测（状态机、积分守恒）在 M4/M8 补充
- admin-web / Flutter：关键流程手工 + 冒烟测试（flutter test）
- M8 安全自测清单全量执行并留档

## ⚠️ 改 `apps/packages/core/**` 前后**必须**跑 core-gate（负责人 2026-10-06）

**背景（2026-10-06 两次被坑）**：core 是**两个 App 共用**的包。并行任务里只要有人把 core 改到
"中间态"（`library` 指令位置写错、依赖包正在改、某个文件半成品），**另一个任务**跑 `flutter test` /
`flutter analyze` 就会整包加载失败，排查成本全落在"不是我改的那行"上 —— 两个任务互相阻塞。

**门禁命令（仓库根，一条命令跑三包）**：

```powershell
powershell -NoProfile -File scripts/tools/core-gate.ps1
# 可选：-NoPub（不触发隐式 pub get，最快/离线）· -Packages apps/packages/core（只跑一包）
#       -TimeoutSec 900（单包超时，默认 600s）· -MaxErrorLines 20（失败时贴多少行关键错误）
```

- **跑哪些**：依次 `flutter analyze` → `apps/packages/core`、`apps/boss-app`、`apps/worker-app`；
- **判定**：**任一包失败（或 flutter 缺失/超时）→ 脚本非零退出**（`exit 1`）；三包全过 → `exit 0`；
- **输出**：每个包**一行结论**（`OK（No issues found!，8.1s）` / `FAIL（3 issues found，9.4s）`），
  失败时再贴最多 `-MaxErrorLines` 行 `error • …` 关键错误 —— 不做全量刷屏；
- **什么时候跑**：
  1. **改 core 之前**（确认起点是干净的，别把别人的中间态当成自己的锅）；
  2. **改 core 之后**（自己别把中间态留给别人）；
  3. 跑 `flutter test` / 出包**之前**（测试加载失败 = 白等一轮）。
- 与 docs/22（开发环境清单）配套：`flutter` 必须在 PATH 上，否则脚本直接 `FAIL` 并给出提示。
- 与「不卡死铁律」一致：单包有超时上限（默认 600s），超时**强杀并判失败**，不会挂住。

## ⚠️ 回归套件里的 `SKIP` 必须"报出原因"：`worker-app-sunset-test` ⑥ 段静默跳过（2026-10-07 修复）

**现象**：`RESULT(sunset): 54 pass / 0 fail | ⑥ 充值会话未实测（见说明）` —— 与基线 56/0 差 2 条，
但 **fail=0、exit=0**，粗看是"全绿"。**差的 2 条是压根没执行**（不是失败）。

**根因**：⑥ 段把前置写成"必须**新增**白名单成功"（不成功就 `SKIP`），而 `recharge_admin` 里**本来就可能已经有
这个账号**（上一轮的残留行）→ `POST /admin/recharge/admins` 回 400「该账号已在充值审核白名单中」→ 走 SKIP；
更糟的是撤销（DELETE）也写在"新增成功"分支里 → 跳过路径**连清理都没有** → 残留行永久存在 →
**此后每一次跑都跳过 ⑥（自锁）**。当时的原始输出（2026-10-06 21:2x 那一轮）：

```
======== ⑥ 充值受限会话（kind=recharge）不受影响 ========
  白名单现状：1 行（并行充值套件可能正在使用；≥4 行则跳过以免互相干扰）
  RAW  ⑥ a POST /admin/recharge/admins（超管把自己加入白名单，仅测试用） → HTTP 400 | message="该账号已在充值审核白名单中" | body={"code":400,"message":"该账号已在充值审核白名单中","data":null,…}
  SKIP ⑥（加入白名单失败：HTTP 400 该账号已在充值审核白名单中）
PASS  ⑥ f 白名单恢复原状（测试数据自清） | 白名单 1 → 1
…
RESULT(sunset): 54 pass / 0 fail | ⑥ 充值会话未实测（见说明）
```

**修复口径**：前置改为**幂等** —— 已在白名单则沿用现有行继续测（INFO，不新增、不删除，**绝不动既有行**，
那可能是负责人的真实配置）；只有"本次真的新增了"才在收尾撤销。同时把跳过原因写进**终结行**，
`⑥f` 从"比行数"改成"逐行比对 `user_id`"。实测（"已在白名单"与"本次新增"两个分支都跑）：**56 pass / 0 fail**。

**规范（对所有回归套件生效）**：任何 `SKIP` 分支都必须 ① 打印**具体原因**（哪一步、什么状态码/文案）
② 把原因带进终结行。**"数字比基线少但 fail=0" 必须能一眼看出是被跳过**，不允许只能靠人去 diff 历史数字。

## ⚠️ 硬规则：**"上传/选文件"类控件必须在真浏览器里用 `DOM.setFileInputFiles` 真注入文件**（负责人 2026-10-07）

**背景（2026-10-07「二维码咋加不了」事故，值得逐字读）**：管理端「充值管理 → 收款码 → 新增收款码」在负责人手里
**选了图、什么都没发生、保存时提示"请先上传收款码图片"**，而**服务端日志里一个 `/admin/media/upload` 都没有**。
上一轮验证脚本（`verify-recharge-ui.mjs`，**本机 `scripts/tmp/` 下的临时脚本、不入库**，仅作反面教材留档）确实"验过"这条链路，但它**没法驱动 `n-upload` 的真实文件框**：
它自己用 `fetch` 打上传接口拿 `mediaId`，再用 Vue 事件路径 `$emit('update:modelValue', id)` 把值灌进表单 ——
于是**"选文件 → customRequest → 真上传"这一段从未被执行过一次**，坏掉的恰恰是这一段
（`MediaUploadField` 同时踩了 naive-ui 的两个开关：`:default-upload="false"` → 选完文件永不 `submit()`；
`:file-list` 传只读 `computed` → `update:file-list` 被丢弃，即使修好前者也扫不到 pending 文件）。
**结论：接口通了 ≠ 控件能用。凡是"上传/选文件"控件，只验接口一律视为未验证。**

- **用什么验**：CDP `DOM.setFileInputFiles`（`DOM.getDocument` → `DOM.querySelector('input[type=file]')` → `setFileInputFiles`），
  把**真实 PNG/视频文件**塞进 file input；再由 Network 域断言**浏览器真的发出了上传请求**（URL + 状态码 + 响应体原文）。
- **要点（不照做就会"验了个假的"）**：
  1. **必须用 CDP `Input.dispatchMouseEvent` 派发真鼠标事件去点上传按钮** —— 原生文件框需要 user activation，
     页面脚本里的 `el.click()` 拿不到，`Page.fileChooserOpened` 不会出现（这就是上一版"没法驱动文件框"的真正原因）；
     需要 `Page.setInterceptFileChooserDialog({enabled:true})` 才会收到 `Page.fileChooserOpened`。
  2. **别把"注入文件"当成"点了按钮"** —— 两件事都要证明：按钮点击是否触达 `input.click()`（可给
     `HTMLInputElement.prototype.click` 打点）、注入后是否真发请求。
  3. **等响应要等 `Network.loadingFinished`**：`requestWillBeSent` 一到就读 `Network.getResponseBody`

## ⚠️ 硬规则：**业务配置类断言必须从服务端/DB 推导，禁止写死数字**（2026-10-08）

**事故经过（本次就为此改）**：负责人 2026-10-08 晚在管理端**下架了 4 个分部**
（三角洲行动·手游/端游、无畏契约·手游/端游）**与 2 个官方馆** → `division` 表 5 行里只剩 `id=1 和平精英` 是
`status=1`、`club` 表 3 行里只剩 1 行 `status=1` → `/divisions/grouped` 由 5 个分部变 1 个。
而回归/冒烟套件里把这些数字**写死**了（`divisions.length === 5`、`byDiv['1'] === 9`、`clubs.length === 3`、
`分部商品数 === 11`）→ **业务配置一变、一批套件集体变红**，排查时间全花在"到底是我改坏了，还是负责人改了配置"。
**写死的数字本身不是被验证的语义** —— 它只是某一天的配置快照。

- **期望值唯一来源 = DB（或接口本身给出的权威字段），不是常量**：
  1. **分部数**：`接口返回的分部数 == DB division.status=1 的行数`（`/divisions`、`/divisions/grouped` 同口径）；
     并且**每个返回的分部都必须满足 `status=1`** —— 这才是要守的语义：**公开接口只暴露已上架分部**。
  2. **商品数**：`接口返回的商品数 == DB 该分部 status=1 AND service_status=1 的条数`；
     加上**集合比对**（公开 id 集合 == DB 已上架 id 集合）→ 一眼看出是**接口漏了**还是**接口多给了**。
  3. **官方馆数**：`/public/clubs` 条数 == DB `club.status=1` 的行数，且返回的每个馆都在该集合里。
- **顺带加真正的护栏（比数字有价值）**：断言**已下架的行不会出现在公开接口里** ——
  取库里真实存在的 `status≠1` 行（分部 / 官方馆 / 商品）的 id，断言它们**不在**公开返回集合中。
  这几条**用当前库里真实存在的下架行做输入**；某类下架行当前不存在就 **`SKIP` 并打印原因**
  （见上文"SKIP 必须报出原因"）——**绝不为凑断言去伪造数据、也绝不在套件里改业务数据**。
- **输出口径（每条断言都要能自证期望值从哪来）**：
  `期望=<N>（来源：DB division.status=1（1 个：1=和平精英）） / 实际=<M>（…）`，
  失败时附方向提示 `（接口漏了…）`/`（接口多给了…）` —— 让人一眼分清"接口漏了/多了"还是"配置变了"。
- **实现入口（唯一取数处，禁止各套件自己拼 SQL）**：`scripts/tools/public-catalog-expectation.js`
  （只读 DB，输出 `activeDivisions / delistedDivisions / activeClubs / delistedClubs / activeProducts /
  delistedProducts / activeProductCountByDivision` + 人类可读的 `sources.*` 来源串）。
  已改的套件：`scripts/tmp/merge-identity-smoke.js`（②③④）、`scripts/tmp/purchase-hint-smoke.js`、`scripts/tmp/hall-smoke.js` ①。
- **负向验证（证明护栏真的会红，而不是永远绿）**：只改**断言输入**、不碰业务数据：
  `PUBLIC_EXPECT_INJECT_DELISTED_DIVISION=<id>` / `PUBLIC_EXPECT_INJECT_DELISTED_PRODUCT=<id>`
  把某个"其实会出现在公开返回里"的 id 假装成下架行 → 护栏断言**必然 FAIL**（运行时打印醒目提示）。
- **不要为了变绿去改业务数据**：`division` / `club` / `product` 一行都不许动 ——
  "把商品补回来/把分部重新上架"是**篡改负责人配置**，比测试红更严重。改的永远是**断言**。
- **配套事实**：`/divisions/grouped` 的 `data` 是**按游戏分组的数组** `[{ gameId, …, divisions: [...] }]`，
  不是 `{ groups: [...] }`（历史套件用 `data.groups ?? data.list` 取不到、落到"把分组当分部"的兜底分支，
  分组数与分部数恰好相同时看不出来）→ 一律用 `flattenGroupedDivisions()`。
- **范围**：本规则同样适用于"负责人上架清单"类工具（如 `scripts/tmp/product-inventory-audit.js`，
  清单来源是负责人上架脚本、属**权威口径**，与"写死断言数字"不是一回事），但**任何把条数/条目标题写进断言的地方
  都要先问一句：这个数字是业务语义，还是今天的配置快照？**

### 同一条规则的另一面：**环境类数字**（数量 / 在线数 / 时序）也必须推导出来（2026-10-08 晚）

**事故经过（客服大厅 e2e 被"原样跑一次"就红了 6 条）**：`scripts/tools/cs-hall-e2e.js` 里有一批断言
把**环境状态**写死了 —— `total === 0`（大厅此刻只有本套件的会话）、`msgCount === 1`（会话里只有 1 条消息）、
`seq === 1`（会话是刚建的）、`onlineCsCount === 0`（此刻没有客服在线）、摘要把"首条消息必须是本次构造的

- **改法（已落地，可照抄）**：
  1. **数量**：与**返回体自身的同源字段 + 分页契约**对齐，而不是写死 ——
     `total === waitingTotal`、`list.length === min(total, pageSize)`（这是真不变量，任何环境都成立）；
     需要"至少包含本套件的 N 条"时只断言**下界 / 相对次序**（`A 在 B 前面`、`在列表里`），不断言绝对下标。

     `preview == 服务端口径(库里实际的首条消息)`），而不是假设它一定是本次发的那条。

## ⚠️ 硬规则：限购 / 环境约束下**怎么挑测试商品**（不许写死 id，也不许放宽断言）（2026-10-08 晚收口）

### 一句话规则

> **"用哪个商品"是套件的前置条件，必须现场按服务端下发的「剩余配额 + 钱包余额」算出来
> （唯一入口 `scripts/tools/test-product-picker.js`）；禁止写死商品 id、禁止取"公开列表第一个"、
> 禁止为了让用例跑通去改 `weekly_limit` 或商品数据。**

### 为什么（三类错误做法都在本仓库真实发生过）

`product.weekly_limit`（迁移 `1796000000000`，负责人 2026-10-05 设定）是**真实业务约束**，
不是测试环境的噪声：商品 137「9.9新人体验单」= **每位用户每周限购 2 单**，
口径 = `status <> 'canceled'` 且最近 7 天（唯一实现 `server/src/modules/order/order.service.ts` 限购段）。
需要"同商品连下 3–4 单"的套件一旦商品挑错，第 3 单起被服务端中文拒绝：

```
400 该商品每位用户每周限购 2 单，你本周已下单 2 单，请下周再来
```

| 错误做法 | 为什么不行 |
|---|---|
| 改 `weekly_limit` / 改商品数据 | **改业务数据**（禁止）。而且负责人下次设回限购，红再来一遍 |
| 写死另一个商品 id | 只是把问题推迟：那个商品哪天也被配上限购，同样的红 |
| 放宽断言 / 少跑用例 | 假绿（见本文件「`SKIP` 必须报出原因」） |

### 正确做法：`scripts/tools/test-product-picker.js`（三套件共用一份，不再各写一份）

```js
const picker = require('../tools/test-product-picker');
// needed = 本套件一次运行**最多同时占用**的订单数（不是"想下几单"）
const picked = await picker.pickProductForOrders({ token: bossToken, needed: 4 });
const prodId = String(picked.id);
console.log(`选商品：候选 ${picked.candidateCount} 件，选中 id=${picked.id}「${picked.name}」单价=${picked.price}`
  + `${picked.limit > 0 ? `（限购${picked.limit}，剩余${picked.remaining}）` : '（不限购）'}`);
if (picked.skipped.length) console.log(`  跳过（配额/余额不足）：${picked.skipped.join(' / ')}`);  // 不许静默
```

算法（四步，全部只读、不下单、不改任何数据）：

1. **候选来源只有一个**：`GET /public/products` —— 它本身就是"当前可下单"的商品集，
   不需鉴权、人人可复现。**不要**用 `/admin/products`：管理端列表不受"分部下架"约束，
   里面混着公开接口访问不到的商品（`media-test` 的 4 条恒红就是这个坑，见下一条规则）。
2. **余额**：`GET /user/wallet`，要求 `单价 × needed ≤ 余额`（测试充值是有限的，
   别让用例卡在"余额不足"这种与被测行为无关的地方）。
3. **限购名额**：配了 `weeklyLimit` 的商品**不自己算窗口/口径**（自己算必然与服务端漂移），
   一律问 `GET /user/orders/weekly-quota?productId=`，要求 `remaining ≥ needed`；
   `remaining === null` = 不限购（名额无限）。额度不够的进 `skipped` 清单并打印。
4. **排序**：**先"不限购"再看单价**。不限购商品名额无限 → 反复跑都稳定命中同一个；
   限购商品的名额是滚动 7 天消耗的，早晚要换商品（一换商品，按单价推导的断言值也变）。

挑不出来时**必须明确失败**：`pickProductForOrders()` 抛中文错误（含候选与跳过原因清单）→
套件以**非零退出**终止，而不是抛 `TypeError`、更不是静默继续。

### 配套三条（缺一不可）

- **`needed` 按"本次运行最多同时占用多少单"填**：`stage14` = 4（主链路 / 并发抢单 / 并发确认 / 取消退款）、
  `leaderboard` = 4（worker01×3 + worker_test2×1）、`commission-rate` = 3（A/B/C 各 1 单）。
- **收尾必须自清**：每周限购只数**非 canceled** 的订单 → 套件必须把本次造出的**非终态**订单
  经管理端接口取消（`POST /admin/orders/:id/cancel`：非终态均可取消 + 全额退款），
  否则"第一次绿、第二次红"（`stage14` 末段与 `dispatch-test` 是同一口径）。
- **共享夹具的临时改动必须无条件还原**（写进 `try/finally`，不是写在主流程末尾）：
  实测事故 —— `leaderboard-test` 临时给 `worker_test2` 授接单权限，中途被限购打断后
  **归还那段被跳过**，于是 `stage14` 的「无接单权限 worker 抢单 → 403」变成假红
  （实测 `status=201`，把排查方向带偏到"权限守卫失效"；守卫是好的，是**前置被上一个套件改脏**）。
  对应地，**依赖"某账号无权限"的套件必须先显式校验该前置**（问服务端要一次权威状态），
  前置不成立就明确报错终止并说明"先跑 test-fixtures.js 复原夹具"，不猜、不静默。

### 另一个反复踩的坑：**不要拿"已被消费掉的状态"当待接单订单**

`stage14` 原先把「无接单权限 worker 抢单 → 403」放在整套流程最后、用**订单2** ——
而订单2 早被"两 worker 并发抢单"抢走了，实测输出：

```
FAIL  无接单权限 worker 抢单 → 403 | 手慢了，订单已被抢走或不可接
```

权限守卫（应最先返回 403）根本没被触达。修法：把这组边界断言移到**订单2 刚建好、仍是
`pending_take`** 的位置，并加一条**前置断言**把"订单2 此刻确实在大厅待接"钉下来。
**断言本身一条没放宽**。

## ⚠️ 硬规则：公开契约**瘦身后断言必须跟进**（不许"为了让旧测试绿"把字段加回去）（2026-10-08 晚）

### 一句话规则

> **公开接口删字段 = 契约变更 → 套件断言必须重写为"当前契约 + 已删字段不再返回"；
> 禁止改服务端把字段加回来，也禁止把断言改成"有就查、没有就跳过"这种放水写法。**

### 判据（怎么确认"这是主动瘦身"而不是"服务端坏了"）

**实现与注释同源**才算数，两处都要看：

- `server/src/modules/home/home-public.controller.ts` 顶部注释（`home()` 上方写明五个字段随死代码删除）；
- `server/src/modules/home/home.service.ts#publicHome()`：`return { announcements: await this.publicAnnouncements(10) }`。

两者一致 → 是**契约瘦身**，重写断言；**两者不一致**（注释说下线、实际还返回，或反之）→ **停下报告**，
不要自己选一个口径去改测试。

### 重写后的断言长什么样（`home-content-test.js` 为范例）

1. **正向（当前契约）**：`/public/home` 200；**键集合逐字相等**（`["announcements"]`）；
   `announcements` 是数组、条目字段完整（`id/title/pinned/createdAt`）、**不含正文** `content`（正文走详情接口）。
2. **负向（契约瘦身钉死，比原断言更有价值）**：对**每一个**已下线字段逐条断言 `!(field in body)`；
   再断言一批**旧命名变体**也不存在（`club_intro` / `clubInfo` / `orderBtn` / `bannerList` / `top_workers`…），
   防止将来"换个名字加回来"绕过检查。
3. **写入口边界要照实写**：管理端 `PUT /admin/home/modules/:key`、`POST /admin/home/banners`
   **仍然存在**（宣传图 2026-10-05 任务②重新启用，App 消费 `GET /public/banners`）——
   "配置能写、公开接口不再下发"才是瘦身；写成"管理端入口已 404"是**照注释猜**，跑一次就红。
   对应断言：管理端写入后，公开聚合**仍不返回**该字段（写完立刻改回原值，不留痕）。
4. **临时数据必须自清**：本套件会临时建公告/宣传图 → 全部进 `try/finally` 删除。
   实测教训：旧断言在"运营能不能写公告"上判错（`operator` **确实持有** `admin:home:write`），
   留下一张 `visible=1` 的「越权宣传图」挂到了公开首页，必须手工清掉 —— 这就是"测试污染线上首页"。

### 同类第二例：**公开可达性也是契约**（`media-test` 的 4 条 `coverUrl`）

`media-test` 原先把测试主图挂到"管理端列表第一条商品"上，而那条商品（id=167）属**分部 6**
（`status=0` 未公开）→ 公开详情 404、公开列表查不到它 → `coverUrl` 断言恒 `undefined`。
**这不是服务端 bug**（`/public/products` 与 `/public/products/:id` 都受"分部下架 = 其商品不再公开"
约束，见 `division/public-division-scope.ts`），而是**测试挑错了被测对象**。
修法：候选 = **公开列表 ∩ 管理端列表**；挑不出来就 `SKIP` 并写明原因，同时仍断言一次
"目标商品公开详情可访问"，把环境事实钉在报告里。

### 同类第三例：**客户端路径字段是服务端下发的契约**（`media-test` 的受保护路径）

受保护媒体的真实路径**含 `/api/v1`**，公开媒体**不含**（`media.service.ts#clientPath` 有完整理由）。
测试断言必须与**服务端下发的 `path` 字段逐字一致**，不能照旧印象写死；
并且要钉一条**反向**断言：少 `/api/v1` 的旧口径路径必须 404（它曾表现为管理端 SPA 回退成
`200 + HTML`，是"付款凭证永久转圈"那类故障的温床）。
