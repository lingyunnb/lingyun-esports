### 4.2 三个货架的口径（**每一条都能被接口验证**）

| 货架 | 口径 | 排序字段 | 数据来源 | 首版能否 0 服务端改动 |
|---|---|---|---|---|
| **为您推荐** | 接单最多（真实接单数降序） | `worker_stats.completed_orders DESC` | `/public/workers/:id` 或 `worker_stats` | ⚠️ 客户端需并发请求 N 次（**N+1，不可接受**） |
| **最近上新** | 新入驻（入驻时间升序） | `worker.created_at ASC` | 只读 SQL 已确认该列存在 | ⚠️ **接口未下发 `createdAt`** |
| **热门点单** | 周榜前列 | 本周期 `leaderboard_entry` 名次 | `/public/leaderboard?kind=week` | ✅ 现成可用 |

**结论：三个货架里有两条拿不到「可排序的字段」，一条能拿到但只能给 3 个人的名次。**
`/public/players` 实测**忽略** `sort` / `sortBy` / `order` / `shelf` 等参数（返回顺序恒为 `w.id ASC`），且它**不返回 `createdAt`、不返回接单数、不返回好评率**。

### 4.3 推荐实现（**需负责人批**）：新增 1 个只读聚合接口

```
GET /public/players/shelves?divisionId=<id>      （无需登录；挂在 PublicCacheInterceptor 的 30s 档）
→ { recommend: [Player], newest: [Player], hot: [Player] }
   Player = { workerId, nickname, intro, avatarMediaId,
              completedOrders,   // worker_stats，与榜单同源
              reviewCount, satisfiedRate,   // order_review 实时聚合，无评价为 null
              joinedAt }         // worker.created_at
```

**为什么必须是服务端（而不是客户端切片）**：
1. **N+1 无法接受**：客户端切片要先拿 14 个人、再为每人打一次 `/public/workers/:id` = 15 个请求；
2. **排序权威必须在服务端**（docs/32 第八节、CLAUDE.md「客户端数据全部不可信」）：同一页面三套排序规则散在客户端，改规则要发版；
3. **一次性满足三个货架**：客户端首屏仍只加 1 个请求（5 → 6，仍并发）；
4. `satisfiedRate` / `completedOrders` 的**口径只有一处**（`ReviewService`），沿用第九节 `satisfiedRateText()` 的「无评价 = 暂无评价」契约。

**首版可降级**：若负责人要求「本周就要上」，可先只上「热门点单」（`/public/leaderboard` 现成），另两个货架走空态——
**不是砍功能，是守「不存在的东西不出现」**（宁缺不假）。

## 六、结构规则 6 的取舍（**必须负责人单独批**）

**规则原文**（CLAUDE.md 结构规则 6）：陪玩/打手展示极简，**允许的字段只有两个：名字 + 介绍**；**禁止出现**：明星陪玩 / 大神 / 单考 / 双考 / **空闲 / 忙碌** / 等级 / **评分** / 单价 / **下单人数** / 语音时长 / 标签胶囊 / 分部副标。

本版设计与它的关系：

| 本版画了 | 是否破规则 6 | 说明 |
|---|---|---|
| 头像（首字字标兜底） | **不破** | 规则 6 的「找陪玩列表 = 头像（若有）+ 名字 + 介绍」；规则 5 也把头像列在容许范围 |
| 名字 | 不破 | — |
| **介绍（2 行截断）** | 不破 | 负责人本轮**点名要的**就是它 |
| 货架标题 + 「查看更多」 | 不破 | 是区块标题与导航，不是**每一行**的字段 |
| **一行元信息：`已接 N 单 · 暂无评价`** | **破**（等价于规则 6 里的「下单人数」与「评分」） | **正式提请单独批**；口径已收窄到两个数、页面上只出现这一次（陪玩列表行与货架卡同一形态） |
| 状态胶囊 / 徽章 / 分部副标 | 不破（**因为根本没画**） | 数据也没有 |

**为什么建议批这一行**：
1. 店面上「这个人接过多少单」是老板决策的**第一信息**，比介绍更硬（介绍可以写得漂亮，接单次数不能）；
2. 货架三个口径（接单最多 / 新入驻 / 周榜前列）**如果没有可见的数字，用户看不出差别**——三个货架就退化成三次随机曝光；
3. 竞品把这一行放在卡片底部（`.companion-meta`，22rpx 灰字），**说明这是行业验证过的信息位**；
4. 数据是现成的、口径是唯一的（`worker_stats.completed_orders` + `order_review` 实时聚合），**零新增成本**。

**若负责人不批**：本行**整行删除**即可（卡片高度 124 → 98），其余设计一字不动 → 退回规则 6 原始口径，**零返工**。
（本版图同时给了「介绍为空」与「介绍已填」两种卡，删除元信息行不影响这两张对照图的价值。）

## 十、⚠️ 上线前置条件（**本版最重要的运营判断**）

实测：**14 位在册打手里 13 人 `intro` 为空**、**14 人头像全为 `null`**；有接单数的 3 人也都是测试账号（`演示工作端 76 单` / `E2E打手 30 单` / `测试工作端2 14 单`），真实名字的 `小云` / `反悔` / `清水` 接单数都是 **0**。

**因此本版设计了三道兜底（都已在图里画出）**：

1. **「介绍为空」的卡片形态**（★本次必需屏）：固定卡高 124dp + 弱化占位「介绍待补充」→ 混合名单不参差、不像坏掉；
2. **空态行写原因**：三个货架各自说明「为什么现在没内容」，让运营一眼看出是「介绍没填」还是「没有单」；
3. **建议的渲染门槛（需负责人选一）**：
   - **方案 A（推荐）**：**有介绍的打手 < 3 人时整个陪玩货架区不渲染**（页面回到现状的「分部 + 官方自营」，与今天逐像素一致）→ 保证服务页**永远不会看起来像坏了**；
   - **方案 B（激进）**：照常渲染，靠占位行撑住 → 首页会长期出现 3 张「介绍待补充」的卡。
   **在 `intro` 补齐（建议：≥ 8 人、每人 ≥ 20 字）之前，建议选 A。**

### 附：为什么不加「陪玩 / 商品」顶部大类切换（审批表第 15 条的理由）

1. **底栏已经有「服务」**（= 本页）。在页内再加一个「商品」标签 = 把商品变成与「服务」并列的一级入口，等于**同一入口出现两次**（结构规则 1）；
2. **两个大类的商品量极不对称**：陪玩 14 人 vs 在架商品 8 个（其中 7 个无封面），给商品开一个一级标签是**用小内容占大位置**；
3. **竞品也没有做大类切换**：它的首页是「货架 + 分类 + 商品流」的纵向结构，切换发生在**分类维度**而不是「陪玩 vs 商品」；
4. **本版给出的替代**：商品入口收敛在页面下半区的「选择分部 → 官方自营」，用户下单走底栏凸起「＋下单」——两个动作各有唯一落点；
5. **如果将来真的要分**：建议做成**页面内的分段控件**（陪玩 / 商品），而不是新的顶部导航项，且需要在商品内容量（至少 ≥ 20 个带封面商品）达标后再评估。
