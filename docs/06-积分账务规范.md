# 06 - 积分账务规范

## 铁律

1. 用户积分**只能由拥有 admin:wallet:grant 权限点的管理员发放**（默认仅超级管理员）；用户不能充值/签到/邀请/赚取/转账
2. 所有积分变化由服务器执行，客户端发送的余额/扣款金额/价格全部不可信
3. **任何**积分变化必须写 wallet_transaction 流水：transaction_no、change_type、amount、balance_before、balance_after、operator_type/id、source、reason、order_id、idempotency_key、ip、request_id
4. 流水只增、不删、不改（前后余额快照不可变）；任何变化可追溯

## change_type 枚举

| 类型 | 方向 | 触发 |
|---|---|---|
| grant | + | 管理员发放 |
| recover | - | 管理员回收 |
| order_pay | - | 下单扣款 |
| order_refund | + | 取消/售后退款 |

## 并发与幂等（下单扣款标准事务，禁 Redis 锁双源）

单事务内按序执行：

1. **条件扣款**：`UPDATE wallet SET balance = balance - :amount WHERE user_id = :uid AND balance >= :amount`，affectedRows=0 → 余额不足，整体回滚
2. 写 wallet_transaction（balance_before/after 用扣款后的值快照，order_id 关联、幂等键落库）
3. 创建 order（服务端按商品 ID 查库真实价格，unit_price/total_amount 落快照）
4. 写 order_price_snapshot（商品全量信息快照，历史订单不随改价变化）
5. 幂等键唯一约束兜底：并发同键时后到者冲突回滚，返回首次订单结果

退款对称：事务内条件增余额 + 写 order_refund 流水；应用层校验"同订单同 change_type 只记一次"。

## 金额守恒校验

流水 `amount` 带符号存储（grant 正 / recover 负 / order_pay 负 / order_refund 正），守恒公式：

```
SUM(wallet.balance) == Σ wallet_transaction.amount（按用户，含全部类型）
```

并发脚本（50 并发同幂等键下单、20 并发抢单、并发发放）均以该等式断言，定期对账脚本复用（M8 落地）。阶段 10 实测：23 项测试含 10 并发同幂等键发放（仅 1 条流水、入账一次）与守恒断言全部通过。

## 发放接口安全

- 权限点 admin:wallet:grant；默认仅超管持有，可显式授予普通管理员（操作留痕）
- 必须字段：userId、amount（正整数）、reason、idempotencyKey；服务端生成流水号
- 高风险操作（发放/回收 ≥ 阈值）需二次确认（M8 落地，阈值 system_setting 配置）
- 发放目标必须存在且非 admin 角色；操作写 operation_log

## 用户侧只读接口

- GET /user/wallet（余额）、GET /user/wallet/transactions（分页流水）
- 用户侧**永不存在**任何增加积分的接口

## 补充（2026-09-21）：用户等级系统

- 5 级，依据 **累计实际消费积分 total_spent**（非余额、非充值）：
  L1 新星会员 ≥0 / L2 进阶会员 ≥500 / L3 精英会员 ≥2,000 / L4 尊享会员 ≥10,000 / L5 王者会员 ≥50,000
- 下单事务内：行锁 user → total_spent += 订单金额 → level = max(level, levelForSpent(新累计))（自动只升不降）
- 退款（取消/超时/售后退款）回退 total_spent（GREATEST(0, -)），等级不自动降级
- 管理端手动调整：权限 admin:user:level（默认仅超管），写 user_level_log（操作人/时间/原等级/新等级/原因）+ operation_log 双重审计
- 客户端不可改等级；等级只在 /auth/me 与公开资料接口下发
- 工作端收益查询：GET /worker/my-wallet = 余额 + 累计结算收入（order_settlement − settlement_reversal 流水聚合）+ 结算次数

## 补充（2026-10-04）：平台抽成比例后台可配（默认 25% = 打手 75%）

### 配置项（唯一真相）

| 项 | 值 |
|---|---|
| `system_setting.setting_key` | `platform_commission_rate` |
| `cfg_value` | `{"value": 25}` |
| 取值语义 | **百分数整数**：`25` = 平台抽 25%、打手拿 75%（不用 `0.25` 小数，避免浮点误差，且与 `order_settlement.worker_percentage/platform_percentage` 的整数百分数语义一致） |
| 取值范围 | **0–50 的整数**（0 = 平台不抽成；50 = 平台最多抽一半），非整数/负数/>50/非数字一律后端 **400 拒绝**（中文错误：`抽成比例必须是 0–50 的整数（单位：%）…`） |
| 默认值 | **25**（负责人 2026-10-04 定案：原 30% → 25%） |
| 权限 | 既有 `admin:setting:read` / `admin:setting:write`（`is_high_security = 0`，即普通管理员也可改；若要收窄为仅超管，把该列置 1 即可，服务端已按超管校验） |

### 读取与结算（禁止再散落硬编码）

1. 结算：`OrderService.completeOrderTx` → `SystemSettingService.platformCommissionRate()` → `splitAmount(total, rate)`
   - 打手比例 = `100 - 抽成`；`workerAmount = round(total × 打手比例)/100`（四舍五入到 0.01），
     **`platformAmount = total - workerAmount`**（而不是各自四舍五入）→ **任何小数金额下 `workerAmount + platformAmount === total` 严格成立**
   - 比例与金额**按结算当时生效值落库**（`order_settlement.worker_percentage/platform_percentage`），历史单据可回溯
2. AI 提示词（祁小山向用户解释结算口径）：`buildSystemPrompt(ctx, rate)` 用同一次配置填充 `{WORKER_PERCENT}` / `{PLATFORM_PERCENT}`
3. 管理端展示：订单详情的比例取自该单 `settlement` 落库值；抽成中心概览的当前比例取自 `GET /admin/commission/stats`（服务端读配置下发）
4. **缓存取舍：不缓存，每次结算/每次生成提示词读一次库**。`setting_key` 有唯一索引，读一行成本可忽略（结算本身还含订单行锁 + 多条流水写入）；
   换来的是「管理端改完立即对新结算生效」且不存在缓存过期窗口导致的对账问题。将来若需缓存，正确做法是在 `SystemSettingService.update`（唯一写入口）里**显式失效**，而不是拍 TTL。
5. **退款冲正不回读当前配置**：已结算订单退款按 `order_settlement` 里的实际金额冲正（`settlement-reversal:{orderId}:worker|:platform`），改比例不会让老单冲正金额错位
6. 读侧兜底：库里该配置被人手工改坏（非 0–50 整数）时，**结算回落默认 25%** 并打 warn 日志，绝不因脏配置算错账
7. **退款时战绩与钱包必须同步回退**（2026-10-06 定案，**不可只做一半**）：退款冲正走 `OrderService.reverseSettlementAndRefund` 时，
   除了钱包侧冲正（`settlement_reversal` / `platform_commission_reversal`）与 `order_refund`，
   **必须在同一事务内**把该单结算时的打手战绩一起退回 —— `worker_stats` 的
   `total_orders -1 / completed_orders -1 / total_amount - 原结算单 order_amount`（`rollbackWorkerStatsTx`）。
   - **判据同一把尺子**：结算加了什么就减什么，金额取 `order_settlement` 落库值（不按当前配置重算）；
     榜单口径（`LeaderboardService.recalc` 的 `NOT_REVERSED_SQL`）用**同一判据**
     「该 `order_id` 是否存在 `settlement_reversal` 流水」→ 钱包、`worker_stats`、榜单三处不会打架。
   - **幂等靠既有的唯一约束**：回退只在 `settlement-reversal:{orderId}:worker` 流水**插入成功之后**才执行，
     而该 `idempotency_key` 有唯一约束（`UQ_wallet_txn_idem`）→ 同一张单**至多回退一次**，不需要第二个幂等键。
   - **绝不出现负数**：用**条件 UPDATE**（三项都够减才动）而不是 `GREATEST(0, …)` —— 
     `GREATEST` 会把「行不存在 / 计数本来就不够 / 已被别的单减过」**静默伪装成"减成功了"**；
     条件 UPDATE 如实返回 `affectedRows = 0`，服务端据此打 warn 日志（异常看得见）。
   - **回退失败不阻断退款**（钱必须退给老板是第一优先），与结算侧「战绩累加失败不阻断结算」同一取舍；
     真发生则打 warn 要求人工核对，钱包侧冲正不受影响。
   - 自证：`scripts/tmp/verify-worker-stats-rollback.js`（+1/-1、幂等、并发恰好一次、不负值、`GET /worker/my-stats` 与库一致）。
8. 打手战绩的**实时读口径**是 `worker_stats`（`GET /worker/my-stats`），榜单快照是另一条路径：
   两者都必须排除已冲正的结算，否则「钱包退干净了、战绩与名次还虚高」。

### 未实施（仅评估）：按分部 / 按游戏差异化抽成

现状是**全局单值**。要按分部/游戏差异化，可行路径见 `platform_commission_rate` 的扩展：`cfg_value` 增加 `byDivision: {"<divisionId>": 20}` / `byGame: {"<gameId>": 22}`，
结算时按 `order.division_id`（订单上已有该字段，无需改订单表）覆盖全局值，管理端在「系统设置」里加「分部覆盖」子表即可。
**代价**：需定优先级（分部 > 游戏 > 全局）、需定义"配置改了的历史订单怎么算"（仍按结算落库值，天然安全）、管理端校验与页面复杂度上升；
且订单快照建议同时落 `commission_rate_source`（用于对账解释）。本次需求只做全局单值，未实施。

## 补充（2026-10-04）：打赏（积分）与退款审批

### change_type 新增（流水枚举扩展）

| 类型 | 方向 | 触发 | 幂等键 |
|---|---|---|---|
| `order_tip_out` | - | 老板打赏出账 | `{客户端 idempotencyKey}:out` |
| `order_tip_income` | + | 打手收到打赏（**100% 过手，平台不抽成**） | `{客户端 idempotencyKey}:in` |
| `balance_adjust` | ± | **余额差额补记**（负责人 2026-10-04）：账本合计与钱包余额不守恒时，把差额补成一条流水，**绝不直接改余额** | 一次性脚本自带唯一键，如 `platform-ledger-fix-20261004` |

`change_type` 列是 `varchar(32)`，**数据库没有 ENUM/CHECK 约束**，wallet 模块也没有代码级白名单（只有管理端流水列表支持按值过滤），因此新增取值不需要改表结构，只需在此登记。

`order_refund` / `settlement_reversal` / `platform_commission_reversal` 的语义与幂等键**不变**——退款审批与售后申诉走同一套。

### 打赏（`order_tip` 表）

1. 仅允许打赏**自己的**订单，且订单状态为 `in_progress` / `pending_confirm` / `completed` 且**已有接单打手**（收款方 = 订单 `worker_id` 反查出的打手账号，客户端不可指定）
2. 单事务内顺序固定：订单行锁 → 累计打赏校验 → 老板钱包行锁读快照 → **条件扣款**（`balance >= amount`，affectedRows 判余额）→ 老板出账流水 → 打手钱包行锁 → 打手入账流水 → `order_tip` 落库；任一步失败整体回滚（**余额不足不产生任何流水**）
3. 金额为**正整数**（钱包 `balance` 是 int，禁止小数）；单次上限 `system_setting.tip_max_per_tip`（默认 500）、**同一订单累计上限** `tip_max_per_order`（默认 1000）——**同一订单允许重复打赏**，受累计上限约束
4. 幂等：`order_tip.idempotency_key` 唯一约束 + 两条流水各自的幂等键；同键重试返回首次结果（`duplicated=true`），**绝不重复扣款**
5. 与订单结算分成比例（`platform_commission_rate`，默认 25%）**无关**：打赏不影响结算金额与比例

### 退款申请（`refund_request` 表）

1. 可申请状态：未开始 / 进行中 / 待确认（`system_setting.refund_apply_statuses`，默认 `pending_take/pending_dispatch/taken/in_progress/pending_confirm`）；**已完成走既有售后申诉**（docs/05）
2. 金额由服务端按订单 `total_amount` 快照计算，客户端**不可传金额**
3. 审批通过 = 复用 `OrderService.adminRefundOrderTx`：未结算订单走 `refundAndClose`（`order_refund` + 幂等键 `refund:{orderId}`）；已结算订单先按**该单结算记录的实际金额**冲正打手与平台，再全额退还——与申诉退款**完全同一套流水与幂等键**
4. **三层防重复**：①提交 `idempotency_key` 唯一约束 ②审批 `UPDATE ... WHERE status='pending'` 判 affectedRows ③订单退款流水幂等键唯一（并前置校验同订单已有 `order_refund` 流水即拒绝）
5. 驳回必须填理由，订单状态不变；通过/驳回均写 `order_status_log` 并给申请人站内通知 + WS

### 站内通知与实时（docs/07）

打赏 / 退款 / 投诉的结果都会写 `user_notification`（类型 `tip_received` / `refund_handled` / `complaint_handled`）并推 WS（`tip:received` / `refund:handled` / `complaint:handled` + `notification:new`）。

- **现象**：**恰好 2 行**不一致 —— `order_settlement` id **374 / 375**（订单 **941 / 950**）：

  |---|---|
  | `order_settlement.platform_amount` | **2.47** |
  | `wallet_transaction`（`idempotency_key='platform:941'` / `'platform:950'`）`amount` | **2.48** |
  | 差 | **恰好 0.01** |

  （`worker_amount` 两侧**完全一致** = 7.43，无差异。）
- **定性：算术必然残差，设计使然。**
  **机制（`server/src/modules/setting/commission-rate.ts:89` `splitAmount()`）**：
  该函数**保守恒** —— 先按打手比例四舍五入到分，**平台 = 总额 − 打手**（而不是各自独立四舍五入），

  对 9.90 元 / 75:25：
  ```
  workerAmount   = round(9.90 × 75) / 100 = 7.43
  platformAmount = 9.90 − 7.43           = 2.47   ← 结算表用这个（保守恒：7.43 + 2.47 = 9.90 ✅）
  独立四舍五入   = round(9.90 × 25) / 100 = 2.48   ← 钱包流水那 2.48 来自另一次独立取整
  ```
  两者相差 **0.01**，是**同一次分账被两处各自取整**的必然结果，**不是错账**。
- **全库核对**：`order_settlement` 自洽性（`worker_amount + platform_amount = order_amount`）
  **66/66 行全部为 0.00 残差**；结算表 `worker_amount` vs 结算流水**无一笔不符**；
  上述 **2 行 0.01** 是全库**仅有的**差异（>1 分的真实错账 **0 笔**）。
- **决定：不改。**
- **理由**：**三处口径不可兼得**（详见 `docs/24a-服务端与数据.md` §2.3 的完整论证与三方案对照表）——
  改流水对齐 2.47 就**要动钱包余额与流水**（违反本文件《铁律》第 4 条）；
  改结算表对齐 2.48 会**破坏全局守恒**（`Σ打手 + Σ平台` 会多出 0.02，且破 `stage14` 断言）。
  **现行方案（结算表吸收差额）是三者中唯一"不碰钱、不破守恒"的选项**，故**保持现状**。

## 2026-10-09 计价单位变更（积分 → 余额，1:1）

### 一、变更内容

**计价的单位从「积分（1 元 = 10 积分）」改为「余额（1 元 = 1 元）」，全部存量金额按 10:1 折算。**

- **折算口径 = A（按 10:1 折算存量金额）**：商品 `88.00` → `8.80`。**真实价格不变** ——
  商品的真实售价本来就在名字里（`8.8保148万（机密）` 对应 88 积分 = 8.8 元），
  折算后价格与名字里的元价**逐条一致**（22 条可解析样本全部一致）。
- **显示口径**：金额用 **¥/元**，钱包叫 **「余额」**。
  **API 字段名一律不改**（仍叫 `points` / `price` / `balance`），只改数值与单位文案 ——
  改字段名会波及三端全部序列化代码，收益为零、风险极高。
- **合规表述保留（一字未改原意）**：余额**仅可用于平台内消费、不可提现、不可转让**；
  平台**不经手资金**、**不接任何支付通道**、**不做自动到账**。

### 四、账目守恒（折算的核心约束）

**`SUM(wallet.balance) == SUM(wallet_transaction.amount)` 折算后必须仍成立。**

⚠️ 天真的「每列各自 `ROUND(x/10,2)`」**会破坏守恒**：本库 `wallet_transaction` 有 **38 行**
金额不是 10 的整数倍（如 `24.75`、`74.25`）。`24.75/10 = 2.475` 半进位成 `2.48`（+0.005），
而它的冲正行 `-24.75 → -2.48`（-0.005）在**笔数不对称**（19 正 18 负）时不会抵消 ——
实测 `SUM(ROUND(amount/10,2)) = 105152.62`，而 `SUM(ROUND(balance/10,2)) = 105152.60`，**差 0.02**。

**解法**（依本节铁律「流水是权威账本，余额是派生值」）：
**`wallet.balance` 不独立折算，而是 = 该用户折算后流水之和**
（`balance = SUM(amount)`）。这样守恒**按构造成立**，而不是靠舍入巧合。

> **禁止**用「最后一条流水的 `balance_after`」当余额：`balance_after` 是逐行独立 ÷10 的结果，
> 自己就带着上面那份舍入不对称，拿它当余额等于把误差搬回去（本迁移首版即如此，守恒差 0.02，已修）。

**代价（已知并接受）**：两个钱包（平台户 `user 14`、`user 1114`）的余额比「直接 ÷10」多 **+0.01**，
合计 0.02 元 —— 这是算术上唯一自洽的结果。

**为什么不去重排 `balance_before`/`balance_after` 让快照首尾相接**：本库快照链**本来就是断的** ——
v0.4.0「数据重置」删过订单类资金流水、再按剩余流水重算余额，于是每个钱包首行仍留着折算前的历史
opening（如 `user 14` 首行 `balance_before = 119.00`，但它**并不计入当前余额**）。用这个 opening
去重放会把早已作废的历史余额**重新灌回**最终余额，反而破坏守恒。故本迁移对快照只做同口径 ÷10，
**不重新解释历史**。

  - `!== 10` → **整段折算跳过**，只做「文案校正 + 类型修正」这类天然幂等的动作。
  - 因此**重复执行不会二次除以 10**（实测：删掉 migrations 记录再跑一次 `up()`，
    商品总价仍是 `4301.50`、订单总额 `780.40`、累计消费 `472.00`，一个数都没动）。
- `down()` 反向同构（闸门 `=== 1` → ×10 并置回 10），`up → down → up` 与 `up → up` 都不产生二次缩放。
- 折算全程在**事务**内（TypeORM `migration:run` 默认 `transaction: 'all'`；若被改成 `none`，
  迁移体内自行 `startTransaction` 兜底）。
- **回滚的固有损耗（如实记录）**：÷10 会丢掉半分位（`24.75 → 2.48`，`×10` 回来是 `24.80`）。
  所以 `up → down` 后全库合计由 `1051526.00` 变为 `1051526.20`（**+0.20**）。
  守恒在每一步都成立，但**往返不是逐字节可逆** —— 这是十进制的性质，不是实现缺陷。
  需要精确还原请用备份：`data/backups/fish_20261010_000344.zip`。

### 六、配置折算

| 配置项 | 变化 | 理由 |
|---|---|---|
| `recharge_config.pointsPerYuan` | **10 → 1** | 1 元到账 1 元余额；同时它就是幂等闸门 |
| `recharge_config.noticeText` | 去掉「1 元 = 10 积分」，改为「按付款金额 1:1 到账余额」+「余额仅可用于平台内消费，不可提现、不可转让」+「平台不经手资金」 | 合规原意逐条保留 |
| `recharge_config.amountOptions` / `minYuan` / `maxYuan` | **不动** | 它们**本来就是元** |
| `level_rules.rules[].minSpent` | **÷10** | 必须跟 `user.total_spent` 同口径，否则等级集体回退 |
| `tip_presets` | `[6,18,38,88]` → `[0.6,1.8,3.8,8.8]` | 余额口径的预设档位 |
| `tip_max_per_tip` / `tip_max_per_order` | 500 → 50 / 1000 → 100 | 不折等于把打赏上限放宽 10 倍 |
| `purchase_points_hint` / `order_notice_default` / `ai_greeting` / `ai_presets` | 文案改写为余额口径 | 都是下发给客户端的中文文案，不许留「积分」 |

**`price_unit`（`product` / `order_price_snapshot`）**：实测库中取值**只有「单」与「20分」**，
**没有任何一行是「积分」** → **数据不动**（负责人给的「若存的是积分就改」条件不成立）。
但 4 个段位商品的**名称里带了旧单位回声**（`铂金 每20分4元=40积分` 的尾巴 `=40积分` 是「4 元 × 10」的旧积分写法），
折算后价格是 4.00 元，留着它就自相矛盾（名字说 40、价格说 4）→ 迁移只删除 `=N积分` 这一段尾巴，
**其余字符逐字不动**；`down()` 按 `=折算后价格×10积分` 精确还原。

### 七、换算逻辑修正（**1:1 下不能再向下取整丢钱**）

- **旧实现**：`points = Math.floor(amountYuan × pointsPerYuan)`。
  在 `pointsPerYuan = 10` 时它**无害**（整数档位 ×10 永远是整数，floor 不生效）；
- **改成 1 之后它是资金差错**：`Math.floor(6.5 × 1) = 6` —— **用户充 6.5 元只到账 6 元，白丢 0.5 元**；
- **新实现**：`points = round(amountYuan × pointsPerYuan, 2)`（先放大 100 倍再取整，规避二进制浮点边界），
  **换算结果 ≤ 0 仍按中文拒绝**；
- `minYuan`/`maxYuan` 与自定义金额校验保持「最多 2 位小数」（`6.555` → 中文 400「最多保留 2 位小数」）；
- 发放路径**一行未改**：仍走 `WalletService.grantInTx()`（金额语义变了，函数不变）。

实测（`scripts/tmp/recharge-test.js`）：**充 6 元 → 到账 6**；**充 6.5 元 → 到账 6.5**（旧实现是 6）；
到账通知文案 `充值申请已到账：+68.00 元`。

## 提现（2026-10-11，打手人工打款）—— **平台经手资金**

> 负责人定案：**做提现，走人工打款**（CLAUDE.md 原「不做提现」铁律已按此改写为
> "提现走人工打款（平台经手资金，二选一：分账或本流程）"）。
> 与充值相反：充值**平台不经手资金**（老板线下付给平台收款码 → 管理员手工发余额），
> 提现**平台经手资金**（平台从余额扣款，再由管理员在微信里把钱打给打手）。
> **仍然没有任何代付/通道/回调**：打款是人工动作，系统只负责"扣款、锁款、记账、留痕"。

### 一、扣款时机（负责人拍板，别再问）

**申请时立即扣**（不是审核通过才扣）：

- 打手点提交 → **同一事务内**从打手钱包扣减并写流水（`change_type='withdraw'`）→ 建 `pending` 申请；
- 因此**申请期间这笔钱不可能被再花、不可能重复提现**（它已经不在钱包里了）；
- 驳回 → **退回余额 + 反向流水**（`change_type='withdraw_reject'`）；
- 打款 → 管理员线下微信转账后回填凭证，状态记 `paid`（**这一步不动余额**：钱在申请时就已经扣了）。
  **回填凭证必须有图**（2026-10-11 收紧）：`pay` 的 `proofMediaId` **必填**、备注可选；
  App 内「管理员身份」受限会话走**专用上传通道** `POST /withdraw/requests/:id/pay-proof`
  （只能给处于 `pending` 的那张申请传图；已打款 → 中文 400）——凭证在 App 里也能传，
  **不再用"备注代替凭证"**。

### 二、流水口径（**两张凭证，一对一**）

| 时点 | `change_type` | 金额符号 | 幂等键 | 前后余额快照 |
|---|---|---|---|---|
| 申请（扣款） | `withdraw` | **负**（如 `-100.00`） | `withdraw:<requestId>` | `balance_before/after` 必写 |
| 驳回（退回） | `withdraw_reject` | **正**（如 `+100.00`） | `withdraw_reject:<requestId>` | `balance_before/after` 必写 |

- **两条都走既有的 `WalletService`**：`withdrawDeductInTx` / `withdrawRefundInTx` 是同一个
  `executeChange()` 的转发入口（**事务内行锁钱包 → 校验 → 改余额 → 写流水 → 幂等键唯一约束兜底**）——
  与"管理员发余额""充值发放"**同一份余额实现**，本模块**不自己 UPDATE `wallet`、不自己拼 `wallet_transaction`**。
- 扣款带 `requireSufficient=true`（**禁负余额**）；退回**不带**（退回只会让余额变大，误置会在异常库里静默失败）。
- `withdraw_request.wallet_transaction_id` 只记**扣款**那条（并受 `UK_wr_wallet_txn` 唯一约束：
  一笔流水只能对应一张申请）；**退回**那条按确定的幂等键反查（不为它加列 —— 少一列就少一处可能与真实流水不一致的冗余）。

### 三、账目守恒（可对账的等式）

对任一打手账号，**任何时刻**：

```
wallet.balance == Σ wallet_transaction.amount(user_id = 该账号)
```

提现链路对这条等式的贡献是**成对出现**的：

- 申请：`balance -= A`，同时新增一条 `withdraw = -A` → 等式两侧同时减 A；
- 驳回：`balance += A`，同时新增一条 `withdraw_reject = +A` → 两侧同时加 A；
- 打款：**只改单据状态，不产生任何流水**（钱在申请时已经离开钱包）。

因此"**在途资金 = Σ pending 申请的 amount**"是一个可独立核算的量：
它**不在任何钱包里**（这正是"申请即扣款"的意义 —— 没有"冻结余额"这种第二真值），
平台的出账义务由 `withdraw_request.status='pending'` 这一张表**唯一**表达。
对账口径：`某打手累计提现 = Σ(withdraw_reject) + Σ(paid 申请的 amount)`。

### 四、幂等（一张申请只能扣一次、只能退一次）

| # | 手段 | 实现 |
|---|---|---|
| ① | 事务 + `SELECT … FOR UPDATE` | 申请：锁钱包行（`wallet.user_id`）；pay/reject：锁申请行（`withdraw_request.id`） |
| ② | **条件 UPDATE 判 `affectedRows`** | `UPDATE withdraw_request … WHERE id=? AND status='pending'` —— **资金动作的唯一判定点** |
| ③ | 幂等键唯一约束 | `wallet_transaction.idempotency_key` 唯一（`withdraw:<id>` / `withdraw_reject:<id>`） |
| 兜底 | 表结构唯一键 | `UK_wr_pending_worker`（同一打手不可能两笔在途）、`UK_wr_wallet_txn`、`UK_wr_idem`（客户端重试） |

重复调用 `pay` → 中文 400「该申请已打款」，**不重复生效**；重复 `reject` → 中文 400「该申请已驳回，不能重复操作」，
**不二次退款**（条件 UPDATE 命中 0 行 → 整体回滚，退款那一步根本没执行）。

### 五、门槛与手续费

- 门槛（`system_setting.withdraw_config`，`is_high_security=1` → **仅超管可写**，读侧**实时读库无缓存**）：
  `minAmount=10`、`maxAmount=2000`、`dailyLimit=1`（每日申请次数）、`feeRate=0`、`noticeText`；
- **未结清申请数上限 = 1 写死在代码里**（`WITHDRAW_PENDING_LIMIT`，与唯一键 `UK_wr_pending_worker` 同源）；
- `feeRate` 当前 **0**，**未参与任何扣款计算**（一旦非 0 必须同时定义"手续费怎么记流水、算不算平台收入"——
  在定义清楚之前不允许把它接进金额链路）；
- 金额一律 `¥`/两位小数，**全模块不出现"积分"**（配置文案里出现"积分"会被写入口直接 400 拒掉）。
