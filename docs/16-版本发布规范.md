# 16 - 版本发布规范

## 版本号

语义化版本 `v{major}.{minor}.{patch}`。第一阶段：v0.1.0（M9 首次可用）→ v0.2.0…；里程碑内的修复走 patch。

## Git 纪律

- 每个稳定阶段一次 commit；commit message 说明实际完成内容（`feat/fix/docs/infra: 描述`）
- 不把大量未测试修改混入一个 commit；重大修改前先形成可恢复版本
- 出现问题时优先回滚到最后一个稳定版本（git revert / 恢复备份），不叠加修改掩盖问题

## 发布检查清单

- [ ] 三端 + 后端全量回归通过（docs/12 里程碑验收）
- [ ] docs 与当日开发日志已更新
- [ ] 数据库备份完成且可恢复（M9 起每次发布前）
- [ ] 安全自测清单通过（docs/09）
- [ ] 环境变量检查：无开发 Token/测试数据进入正式配置
- [ ] 打 tag：`git tag v0.1.0`

## 回滚

1. 代码回滚：`git revert` 或 checkout 到上一个稳定 tag
2. 数据回滚：恢复最近备份（docs/10）
3. 回滚后先验证再对外恢复服务

## 云端更新流程（2026-09-22；2026-09-23 扩至双端）

1. 构建：`flutter build apk --dart-define=APP_VERSION_CODE=N --dart-define=APP_VERSION_NAME=x.y.z`（版本码必须单调递增且与后台上传记录一致，否则会造成重复提示）
2. 后台「版本更新」页上传 APK 并填写版本信息/更新说明/是否强制（页面顶部可切换 **老板端 / 工作端**，两端通道独立）
3. 客户端启动自动检测（服务端比较版本码并按 appType 隔离通道），有新版弹窗（普通=可稍后；强制=阻断主界面）
4. 下载（进度/百分比/大小）→ sha256 校验 → 系统安装流程（FileProvider，不绕过安全机制）
5. 只允许启用中的版本被下载；`app_version.app_type` 区分 boss / worker，**工作端永远不会收到老板端安装包**

更新能力由 `apps/packages/core/lib/src/update/` 提供（双端共用：AppUpdater 检测/下载/校验、UpdateCenter 流程状态、更新弹窗、强制更新阻断页）；
各端启动时必须 `UpdateCenter.instance.configure('boss' | 'worker')` 声明自身通道，未配置直接抛错（防误检另一端）。

> ⚠️ 首装前提：老版本 App 里没有更新能力，不会自己弹出更新（工作端 1.0.9 之前的版本尤其如此）——
> 首次必须手动安装一次带更新能力的版本，之后所有后续版本才会自动推送。

## 发布标准动作（2026-09-23，负责人要求；双端）

每次**老板端或工作端**更新完成后，执行对应脚本：

```bash
node scripts/release-boss.js   11 1.1.0 "更新说明" [--force] [--install]   # 老板端通道
node scripts/release-worker.js 11 1.1.0 "更新说明" [--force] [--install]   # 工作端通道
# 等价：node scripts/release-app.js <boss|worker> 11 1.1.0 "更新说明"
```

脚本自动完成：构建对应端 arm64 APK（注入版本码/版本名/隧道地址）→ 上传到该端云端通道 → 停用该端旧启用版本（不影响另一端）→ 验证该端云端最新。
规则：同一端内版本码单调递增；默认非强制（用户可选稍后），重大修复用 --force；手机连接时加 --install 同步推装。

## ⚠️ 发布脚本的管理端账号必须走 `RELEASE_ADMIN_*`（负责人 2026-10-06 技术债收敛）

**背景（与回归套件同一个坑）**：`scripts/release-app.js`（`release-boss.js` / `release-worker.js` 的共用实现）
原先**只能**读 `server/.env` 的 `ADMIN_USERNAME` / `ADMIN_PASSWORD` 登录管理端上传 APK，
而本机那对值是**负责人本人的超管账号**。按 docs/04 的**单设备铁律**（primary ↔ primary 互斥），
**每发一次版就可能把负责人在别处（浏览器管理端 / 手机端）的登录顶掉**（表现为"莫名被登出"）。

- **取账号的唯一入口**：`scripts/tools/release-admin.js`（与回归的 `scripts/tools/regression-admin.js` 同构）。
  发布路径**禁止**再自己读 `.env` 的 `ADMIN_*` —— 多一处就多一次踩坑机会。
- **取值优先级（唯一判定）**：`RELEASE_ADMIN_USER` / `RELEASE_ADMIN_PASSWORD` **>** `server/.env` 的 `ADMIN_*`。
  推荐指向**专用测试超管**（有版本上传权限即可，非 owner）：

  ```powershell
  $env:RELEASE_ADMIN_USER='<临时测试超管>'
  $env:RELEASE_ADMIN_PASSWORD='<该账号口令>'
  node scripts/release-boss.js 84 1.11.28 "更新说明"
  ```

- **未设置时的行为**：**照旧用 `.env` 里那个账号**（不改回退账号：悄悄换账号会让人看不出"这次到底用了谁"），
  但打印醒目中文警告（写明用的是哪个账号、为什么会顶掉真人会话、建议怎么改）。
- **发版前先预检"这次会用哪个管理端账号"（不登录、不构建、不发任何请求）**：

  ```powershell
  node scripts/tools/release-admin.js --check-admin
  node scripts/release-boss.js   --check-admin      # 包装入口同样支持
  node scripts/release-worker.js --check-admin
  ```

- **影响面为零**：本收敛**只决定"用谁登录"**；上传、停用旧版本、云端校验、`--force` / `--install` 等行为一行未改。
- 与回归入口的关系：两者**刻意分开命名**（`REGRESSION_ADMIN_*` vs `RELEASE_ADMIN_*`）——
  回归跑得勤、发布跑得少，分开命名可让"哪一次动作用了谁的会话"事后可分辨；
  想让两边共用同一个专用测试超管，把那两组变量都设成同一个账号即可。
- 配套坑：**不要**为了发版去改 `server/.env` 的 `ADMIN_USERNAME`（改完忘了还原 = 更隐蔽的事故，
  而且 `.env` 被 gitignore，git 证明不了它没被改过）。
