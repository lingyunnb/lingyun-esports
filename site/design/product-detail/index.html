数据行的诚实提醒：本机 33 个在售商品的 estimateDurationMin 全部等于 30（一个统一默认值，不是逐商品真实时长）。所以三套稿里这一列都写成"约 30 分钟"， 但实施前建议管理端把它标成必填并逐个填真值，否则用户点开 10 个商品看到 10 个"约 30 分钟"， 会立刻觉得这行是凑数的 —— 这正是 docs/21 说的"编造的装饰数据"。

提示条文案（具体可验证 · 与后端实现对齐）：
未接单可随时取消并全额退回积分；超 24 小时无人接单，系统自动取消并退款。
两个数字都不是编的，可在后端找到：取消路径 cancelByUser（待接单可取消，全额退款，状态落 canceled）； 24 小时来自 system_setting.order_pending_take_timeout_hours（默认 24）。 实施时这两个数必须由接口下发（不能写死在 App 里），管理端改配置后文案自动跟着变。

推荐：方案甲。依据：① 负责人的原话是"所有下单须知在管理端写"—— 甲让 33 个商品一次到位，乙要靠人记住每个都写；② 下单须知里真正会变的是平台规则（退款、接单时限、积分规则）， 这类话术天然是全局的；③ 保底/包出这类例外才需要逐商品，正好用"覆盖"表达； ④ 甲多出来的成本只有一个页面，而它同时解决了乙最容易出的问题——新商品没有须知。

但不要一次做全：建议第一步只做「全局默认 + 商品级覆盖」两个字段 + 一个编辑页， 版本历史/定时生效/下单快照留到第二步（它们是锦上添花，且第一步做完就已经满足负责人要求）。

预览怎么做（"必须能在管理端看到用户在 App 里长什么样"）：管理端编辑区右侧固定一个 390×844 的手机预览，直接复用 App 同一份渲染规则（同一段落样式、同一提示条、同一「下单须知」小节标题）。 编辑框内容变化时预览实时更新；不要另外写一套"预览专用样式"——两套样式必然走偏， 这是"管理端写的和用户看到的不一样"的常见根因。

  • 提示条里的 24 是占位符渲染结果 —— 管理端改不了它， 它来自「系统设置 → 订单超时」。文案里的数字只能有一个来源，否则两处会打架。

五之三、是否需要版本 / 生效时间（我的判断）

能力要不要理由
保存留史 + 版本号要（全局默认页） 下单须知是用户下单时依赖的规则，出事要能回溯"当时写的是什么"。成本极低（一张历史表或一列 JSON）
下单时写快照到订单要，默认开 订单表已有商品快照的成熟做法，复用同一思路。没有它，规则一改，历史订单就说不清依据
定时生效第二步再做 只有大促/规则切换才用得上，属于低频。先做「立即生效」，字段留好 effectiveAt 即可
商品级也做版本不要 商品编辑已有 updatedAt 与操作日志，再叠一层版本只会让页面变复杂

六、下单须知的数据方案（落库 / 下发 / 兼容）

层现状需要新增
商品表 product 已有 description / detail / serviceFlow / serviceRules / attention （5 个 TEXT，目前基本是空的：抽查 137 只有 description 有值，其余 4 个为空） 加 order_notice TEXT NULL —— NULL = 继承平台默认（空串也归一化成 NULL）
系统设置 system_setting 已有成熟的 key/value 表 + 中文校验 + 超管专属权限（如 platform_commission_rate） 加一条 order_notice_default（TEXT）+ 一条 order_notice_version（INT，保存时 +1）
公开接口 GET /public/products/:id 目前 直接 ...product 整体铺开返回实体 —— 新增列会自动出现在响应里，不加白名单 在 service 里做一次解析：把 orderNotice 填成最终生效文案，并附 orderNoticeSource（default / product）
列表接口 已经做了列裁剪（select 白名单，明确排除 5 个大 TEXT，为弱网首屏优化） 什么都不做 —— 须知不进列表，别把刚裁掉的体积加回去
缓存 详情接口挂在 PublicCacheInterceptor 的 30s 微缓存下 无需改动，但要知道：管理端改完最多 30s 生效。若要求"改完立即看到"，需在保存时清该商品的缓存键
订单表 已有商品快照字段 可选：加 order_notice_snapshot TEXT（下单时那一版）
迁移 TypeORM migration，只加列 / 加设置项 纯新增、无破坏：老商品 order_notice 为 NULL → 自动跟默认； 默认初始值直接写入现在这段通用须知，上线第一天每个商品就有须知，不会出现空窗
一条重要的取舍：不要复用 attention（注意事项）字段。 它语义是"这个商品的注意事项"，而负责人要的是平台级下单须知（退款、接单、积分规则）。 混用会出现"改了平台须知，把商品自己的提醒也冲掉"。两个字段各管一件事： order_notice = 平台的规则（可继承全局）， attention = 这个商品的额外提醒（永远只属于它自己）。

现有 4 个空 TEXT 字段怎么办：detail / serviceFlow / serviceRules 目前全空、 且现有详情页会把它们各渲染成一个卡片（空则不渲染）。建议本次只保留 description（商品描述）一个， 其余三个要么在管理端明确用途后填起来，要么后续合并 —— 现在它们对用户是"不存在的东西"，符合 docs/21 就不该出现在设计里。
下发与解析（伪代码）
// 详情接口里解析生效文案 const def = await settings.value( 'order_notice_default', DEFAULT_ORDER_NOTICE); const src = (p.orderNotice ?? '').trim(); return { ...product, orderNotice: src || def, orderNoticeSource: src ? 'product' : 'default', orderNoticeBar: NOTICE_BAR_TEMPLATE, // 含真实超时小时数 };
客户端只做两件事
  • 有 orderNotice 就渲染「下单须知」小节，没有就整节不存在 （不显示空标题、不显示"暂无"）
  • 不拼任何规则文案 —— 与现有每周限购同一原则（服务端下发、客户端只展示）
    /user/orders/weekly-quota 已是这个模式的先例，照它做即可
权限
  • 读：所有管理员可看
  • 写：建议沿用超管专属（admin:setting:write）， 与 platform_commission_rate 同级 —— 这是会影响全平台订单的规则文本
  • 写操作进 operation_log（谁、改前、改后、版本号）
