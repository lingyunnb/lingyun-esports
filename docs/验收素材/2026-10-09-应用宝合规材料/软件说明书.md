### 1.2 软件用途

本软件是一套面向**游戏陪玩与代练服务**的线上交易与服务平台，解决四件事：

1. **把陪玩服务商品化**：把"段位上分 / 代打 / 娱乐陪玩 / 指定护航"等服务按"游戏 → 分部（游戏 + 端游/手游）→ 分类 → 商品"四级目录挂到线上，价格、图片、视频、下单须知全部由管理端动态配置，新增游戏不需要改客户端代码。
2. **把下单到结算跑成闭环**：老板（下单用户）用平台积分下单 → 订单进入接单大厅 → 打手抢单或管理员派单 → 打手服务、提交完成 → 老板确认完成 → 服务端按后台可配的抽成比例自动分账（老板端与打手端钱包同时入账并写流水）。
3. **把沟通链路放进同一个 App**：老板端一个 App 内同时承载「老板态」与「打手态」，老板在「我的 → 身份」里用打手账号切换到打手态接单；好友私聊、客服会话、老板与打手的一对一直聊三类消息走同一套实时通道。
4. **把资金与积分管住**：平台不经手资金——充值走"线下扫码付款 + 管理端人工审核后手工发积分"；用户不能自助充值、签到、邀请或转账，任何积分变化都写独立流水并保留前后余额快照。

### 1.3 适用对象

| 角色 | 入口 | 主要诉求 |
|---|---|---|
| 下单用户（老板） | 老板端 App「祁连山电竞」 | 浏览分部与服务商品、下单、跟进订单、联系客服、查看积分与等级 |
| 打手（工作人员） | 老板端 App 内「打手态」 | 接单大厅抢单、处理订单、接待客服咨询、查看收益 |
| 客服人员 | 老板端 App 内打手态「客服」页 / 管理端 | 接入老板咨询、处理会话、释放会话 |
| 平台管理员 | Web 管理后台 | 用户与打手管理、目录维护、订单与派单、积分发放、充值审核、排行榜、系统设置、操作日志与安全审计 |
| 超级管理员 / 平台所有者 | Web 管理后台 | 角色与权限点配置、高安全配置项（抽成比例、绑定上限、充值配置、工作端到期时间） |

## 第三章 功能模块说明

### 3.1 老板端功能（品牌名「祁连山电竞」）

#### 3.1.1 启动与首页

App 冷启动先显示品牌启动屏：纯白底、品牌雪山标、「祁连山电竞」与一行副标题（陪玩 · 代练 · 护航），启动屏以浮层形式压在应用之上，最短 400 毫秒、最长 1200 毫秒，200 毫秒淡出，**永不阻塞启动**，每次进程只显示一次。

启动完成后进入**服务页（首页）**：按"分部"陈列官方自营服务（分部 = 游戏 + 端游/手游，例如"和平精英·手游"通栏主卡、"三角洲行动·手游"、"三角洲行动·端游"）；每一分部卡下方是分类与商品入口；页面顶部为宣传位与充值入口条，底部为五个导航位（服务 · 订单 · ＋下单 · 消息 · 我的）。

【图 3：首页实色底与整体版式】（文件：docs/验收素材/2026-10-08-启动闪屏实色底/startup_home_solid.png）

【图 4：全页背景为统一冷灰蓝实色底（无渐变装饰）】（文件：docs/验收素材/2026-10-08-启动闪屏实色底/startup_backdrop_solid.png）

**首页信息架构的设计约束**（写入项目规范的硬要求）：

- 同一入口只出现一次：底部导航已有服务/订单/消息/我的，顶部导航不再重复这些名字。
- 不存在的东西不出现：和平精英只有手游，则该分部不显示"端游"选项；平台筛选仅当该游戏有多个平台时才出现。
- 平台只做官方自营，不出现"推荐俱乐部/关注俱乐部"等多档标签。

#### 3.1.2 下单（服务商品购买）

下单入口有三处：底部导航中间的凸起「＋下单」、商品详情页的「立即下单」、以及"找陪玩 → 指定打手下单"。

下单页按分部与分类展示服务商品，商品卡显示：商品名、价格（积分）、徽标（如"热门"）、周期与限购提示。点击商品进入详情页，详情页展示：主图与多图画廊、可播放的视频、服务说明、**下单须知**（商品级覆盖，未配置则继承全局默认）、可选的游戏区服/段位等游戏特有字段（由后台 `game_config` 动态渲染）。

【图 5：管理端商品/目录页（决定客户端展示的商品与价格）】（文件：docs/验收素材/2026-10-08-管理端操作列/after-1600-catalog.png）

下单流程（详见第四章 4.1）提交后，服务端在同一事务内完成：条件扣款、写积分流水（含前后余额快照）、创建订单、写订单价格快照、写状态日志。**订单金额一律以创建时的服务端快照为准，商品后续改价不影响历史订单。**

#### 3.1.3 订单

底部导航「订单」页按状态分区：待接单 / 已接单 / 进行中 / 待确认 / 已完成 / 已取消 / 售后。订单详情页展示：

- 订单号、下单时间、商品与数量、订单金额（积分）与下单时快照；
- 接单打手信息（工号 + 昵称）与服务进度；
- 状态时间轴（每一步的来源与时间，来自订单状态流转日志）；
- 结算信息：平台抽成比例与打手所得比例（按结算当时生效比例落库展示）；
- 底部操作：取消订单、确认完成、申请售后、申请退款、联系客服（直接进入与该订单相关的客服会话）。

订单状态机完全由服务端控制，客户端不能直接改状态；非法跳转一律被服务端拒绝并写安全审计（详见 `docs/05`）。

#### 3.1.4 找陪玩与指定打手

「找陪玩」列表**只显示两个字段：名字 + 介绍**（介绍由管理端填写）。这是写进项目规范的硬约束——不显示评分、等级、单价、接单数、标签胶囊等字段；需要这些信息时进入打手详情页查看。

老板可以在找陪玩列表中选择某位打手发起"指定下单"；**指定下单只会看到在该分部有接单权限的打手**，无权限的打手不会出现在候选里。

#### 3.1.5 排行榜

排行榜支持**分部榜**与周榜/月榜切换；每行只显示名次、头像、名字与数值，分部由页面上方的胶囊决定，不写进每一行。榜单数据由服务端按结算流水聚合重算，退款冲正后的战绩会被排除（避免战绩与名次虚高）。

【图 6：管理端排行榜页（榜单口径与快照维护入口）】（文件：docs/验收素材/2026-10-08-管理端操作列/after-1600-leaderboard.png）

#### 3.1.6 消息（三类分区）

消息页只有三类会话，各有独立分区：

| 分区 | 说明 |
|---|---|
| 好友私聊 | 好友申请、同意/拒绝、删除、搜索（支持中文 ID）、系统通知；会话与消息走同一实时通道 |
| 客服 | 与平台客服的一对一会话。老板提交咨询后进入"等待接入"，由有客服权限的打手在客服大厅**抢占式接入**（先到先得） |
| 打手 | 老板与为其服务的打手的一对一直聊（订单接单成功后自动建立） |

打手态下消息页同样三类，其中"打手"分区替换为"老板"分区；**好友分区为条件显示**——只有当该账号确实存在好友会话时才出现，没有就整段不渲染（不显示空段）。

【图 7：客服会话（老板侧）图片消息正常加载】（文件：docs/验收素材/2026-10-07-登出与图片路由/chat_20_image_ok.png）

消息能力细节：文本、图片、视频、表情、撤回、已读位点（单勾=已送达 / 双勾=已读）、未读汇总、历史分页；发送方一律携带客户端消息 ID 用于幂等。

#### 3.1.7 我的（含身份切换）

「我的」页包含：个人资料（头像/背景/昵称/中文 ID）、积分卡（余额与流水入口）、我的订单、服务宫格、会员成长进度、身份（绑定打手账号）、设置（主题、版本更新、退出登录）。

**身份分组是"一 App 双态"的入口**：老板在「我的 → 身份」里输入打手账号与密码完成绑定，随后可一键切换到打手态；打手态顶部有 28dp 的身份细带提示"当前在打手态"。

#### 3.1.8 退款与售后

- **退款申请**：对**未结束**订单（待接单 / 待确认派单 / 已接单 / 进行中 / 待确认）提交退款申请，进入管理端审批；审批通过后订单取消并全额退回积分，驳回则订单状态不变且必须填理由。
- **售后申诉**：对**已完成**订单在申诉窗口期内发起申诉，由管理员裁决（驳回回到已完成；支持则取消并退款）。

两条路径都写状态日志留痕；审批使用条件更新，重复审批被拒绝，绝不二次退款。

#### 3.1.9 充值（线下收款 + 人工审核）

合规设计要点（写进项目规范的红线）：

- **平台不接任何支付通道**：没有支付 SDK、没有支付回调、没有支付单号，全站不出现"支付成功"字样，只有"已发放"（表示积分已由管理员手工发放）。
- 老板在充值页选择金额（或自定义金额，受最小/最大金额配置约束）→ 页面展示管理端指定的收款码图片 → 老板**在平台外扫码付款** → 上传付款截图 → 提交充值申请。
- 管理员在管理端或 App 内的"管理员身份"里核对截图后**手工发放积分**；发放复用与超管手动发积分完全相同的服务端事务，绝不重复加分（同一申请只能发放一次）。
- 积分换算：`积分 = 向下取整(金额 × 每元积分配置)`，不向上取整（平台不会多发）。
- **不做提现**：用户永远不能自行加分或提现。

#### 3.1.10 积分与等级

积分规则（第一阶段铁律）：用户积分**只能由拥有发放权限的管理员在后台手动发放**；用户不能自行充值、签到、邀请、通过订单获得或转账积分。所有积分变化由服务端执行并写流水（流水号、类型、金额、前后余额快照、操作者、来源、关联订单、幂等键、IP、请求 ID），流水只增不删不改。

会员等级共 5 级，按**累计实际消费积分**自动升级（只升不降）：L1 新星会员 / L2 进阶会员 / L3 精英会员 / L4 尊享会员 / L5 王者会员。会员体系只属于老板端账号，工作端账号不设等级。退款会回退累计消费（不会自动降级）。

### 3.2 打手态功能（在老板端 App 内）

打手态是老板端 App 内的受限第二态，**只显示三处：接单大厅 / 消息 / 我的**；底部导航只有三项（无第 4 个 tab，除非账号有客服权限时出现第 4 项「客服」）。

#### 3.2.1 身份绑定与切换

1. 老板态「我的 → 身份」输入打手账号（登录名 / 中文 ID / 工号）与密码完成绑定；
2. 绑定成功后签发的是一枚**伴随会话**（companion）：它**只顶掉同一账号的伴随会话，绝不顶掉打手账号原本的登录**（打手在自己设备上照常登录，互不影响）；伴随会话有效期 12 小时，到期需重新输入打手账密切换；
3. 服务端对伴随会话执行**每请求实时校验**（无缓存）：绑定仍为 active、绑定里的打手与会话主体一致、打手账号未封禁、打手档案在职、老板账号未封禁；**解绑即刻失效**（已建立的实时连接会被主动断开）；
4. 伴随会话是**受限会话**，只放行打手族接口、消息族接口、个人资料读取与认证类接口（允许清单制，默认拒绝）；访问订单、钱包、身份、改密码、管理端接口一律 403；
5. 解绑保留历史记录（不物理删除），并写身份审计日志（谁、何时、什么原因、涉及哪个绑定）。

## 第四章 主要操作流程

### 4.1 下单流程（老板侧）

| 步骤 | 操作 | 系统行为 |
|---|---|---|
| 1 | 打开 App，冷启动品牌屏 | 校验本地会话有效性，进入服务页 |
| 2 | 在服务页选择分部与商品 | 客户端按服务端下发的分部、分类、商品渲染；不写死任何游戏逻辑 |
| 3 | 进入商品详情，查看服务说明与下单须知 | 游戏特有字段（区服/段位等）由后台配置动态渲染 |
| 4 | 点击「立即下单」（或底部「＋下单」） | 校验登录态与积分余额，展示确认信息 |
| 5 | 提交订单（可填备注、游戏区服） | 服务端单事务：条件扣款 → 写积分流水（含前后余额快照）→ 创建订单 → 写价格快照 → 写状态日志 → 累计消费与等级更新；任一步失败整体回滚 |
| 6 | 订单进入接单大厅 | 订单状态"待接单"，对大厅可见；实时通知在线打手 |
| 7 | 在「订单」页跟进 | 状态变化实时推送；可取消（待接单阶段）、可申请退款、可联系客服 |

**幂等设计**：客户端提交时携带客户端请求 ID（幂等键），服务端以唯一约束兜底，重复提交只产生一笔订单并返回首次结果。

### 4.2 抢单流程（打手侧）

| 步骤 | 操作 | 系统行为 |
|---|---|---|
| 1 | 老板态「我的 → 身份」输入打手账密 | 校验打手档案在职、账号未封禁；建立绑定并签发伴随会话（12 小时） |
| 2 | 切换到打手态 | 进入打手态三处（接单大厅 / 消息 / 我的）；顶部显示身份细带 |
| 3 | 打开「接单大厅」，按分部筛选 | 只列出该打手有权限的分部；无权限返回空列表 + 中文提示 |
| 4 | 点击「抢单」 | 服务端实时校验接单权限、进行中订单上限、订单仍为待接单；用条件更新判定并发，只有一人成功 |
| 5 | 抢单成功 | 订单状态"已接单"，自动建立老板与该打手的一对一会话；双方收到实时通知 |
| 6 | 点「开始服务」→ 服务完成后「提交完成」 | 每次流转先校验迁移表，再写状态日志 |
| 7 | 老板确认完成 | 进入结算流程（见 4.3） |

### 4.3 结算流程（服务端自动分账）

| 步骤 | 说明 |
|---|---|
| 1 | 老板在订单详情点击「确认完成」（或管理员强制完成） |
| 2 | 服务端开启事务并对订单行加锁，校验：当前状态允许完成、订单有接单打手、打手档案在职 |
| 3 | 读取**当前生效的抽成比例**（系统设置项，管理端可改，改完下一单立即生效，读侧无缓存） |
| 4 | 服务端分账：打手所得 = 四舍五入(订单金额 × 打手比例)；平台所得 = 订单金额 − 打手所得（保证两者之和严格等于订单金额） |
| 5 | 打手钱包入账（工作端自己的钱包），平台账户入账；双方各写一条流水（含前后余额快照与订单关联） |
| 6 | 写结算记录（记录**结算当时**的打手/平台比例，历史单据可回溯）、状态流转、状态日志、销量累加 |
| 7 | 三重幂等保证一个订单只结算一次：订单行锁串行化 + 状态检查 + 结算记录唯一约束；重复请求返回中文提示且不重复加分 |
| 8 | 打手战绩与榜单累加；若订单后续被退款，同一事务内冲正结算并回退战绩 |

### 4.4 客服流程（老板咨询 → 客服接入）

| 步骤 | 操作者 | 说明 |
|---|---|---|
| 1 | 老板 | 在消息页「客服」分区发起咨询（或从订单页「联系客服」进入） |
| 2 | 系统 | 会话进入"等待接入"，向所有在线且有客服权限的打手广播新咨询（含预览与等待时长） |
| 3 | 客服 | 在打手态「客服」页看到待接入列表（等待时长、消息条数、最后一条预览），点击「接入」 |
| 4 | 系统 | 以数据库唯一约束 + 生成列保证"一个会话同时只被一个客服接入"；并发点击只有一人成功；成功后提示"已接入"并通知其他客服该条已消失 |
| 5 | 双方 | 在会话内实时收发文本/图片/视频/表情，支持撤回与已读位点 |
| 6 | 客服 | 处理完毕可释放会话（回到等待池）或关闭会话；老板再次发消息可重新进入等待池 |

### 4.5 充值流程（线下付款 + 人工审核）

| 步骤 | 操作者 | 说明 |
|---|---|---|
| 1 | 老板 | 进入充值页，选择金额（或输入自定义金额，受最小/最大约束） |
| 2 | 系统 | 展示管理端配置的收款码图片与说明文案；提示"线下扫码付款后上传截图" |
| 3 | 老板 | 在平台外扫码付款，回到 App 上传付款截图并提交申请（同一用户待审申请数受上限约束） |
| 4 | 管理员 | 在管理端「充值管理」或 App 内"管理员身份"查看待审列表，点击某条查看付款截图（专用凭证通道，收窄到"这张申请的那张图"） |
| 5 | 管理员 | 点击「发放」并二次确认 → 服务端单事务：校验申请仍为待审、行锁串行化、复用积分发放事务加分、写流水（幂等键 = 充值申请号）、回写审核人与审核时间、发站内通知 |
| 6 | 老板 | 收到"充值申请已到账：+N 积分"通知，积分立即到账；若被驳回则收到含理由的通知 |

**合规约束**：全站不存在"支付成功"字样与任何支付通道；`granted` 状态只能由管理员手工触发，没有任何定时任务或回调路径能自动到账。

### 4.6 身份绑定流程（一 App 双态）

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1 | 老板态「我的 → 身份」→「绑定打手账号」 | 输入打手账号（登录名 / 中文 ID / 工号）与密码 |
| 2 | 服务端校验 | 账号或密码错误统一返回同一句中文（不泄露账号是否存在）；校验打手档案在职、账号未封禁、当前绑定数未达上限（上限后台可配，默认 1，范围 1–10） |
| 3 | 建立绑定 | 单事务内对老板账号行加锁（并发绑定串行化）+ 两个唯一键兜底（一个打手同时只能被一个老板绑定；老板侧槽位不超上限） |
| 4 | 签发伴随会话 | 只顶掉同一账号的伴随会话，**绝不触碰打手本人的登录**；有效期 12 小时 |
| 5 | 切换打手态 | 客户端进入打手态三处；每请求实时校验绑定与账号状态，解绑即刻失效（含断开已建立的实时连接） |
| 6 | 解绑 | 保留历史行（status=unbound）+ 吊销伴随令牌 + 断开实时连接 + 写身份审计日志；老板可随时重新绑定 |
| 7 | 封禁/删除账号 | 服务端把该账号**两侧**的 active 绑定全部置为解绑（对称释放），并在响应中回带释放结果；解封后不自动恢复绑定 |

### 4.7 退款与售后流程

| 场景 | 入口 | 服务端行为 |
|---|---|---|
| 未结束订单退款 | 订单详情「申请退款」 | 生成退款申请（记录申请前状态与理由）→ 管理端审批 |
| 审批通过 | 管理端 | 订单取消 + 同事务全额退回积分；若该单已结算，先按结算记录冲正打手与平台，再全额退老板；**同一事务**回退打手战绩 |
| 审批驳回 | 管理端 | 订单状态保持不变，必须填理由，写状态日志 |
| 已完成订单售后 | 订单详情「申请售后」 | 生成申诉记录 → 管理端裁决（驳回回已完成 / 支持则取消并退款 + 冲正战绩） |

### 4.8 目录与商品维护流程（管理端）

1. 新增或选择游戏 → 2. 配置分部（游戏 + 平台）→ 3. 维护分类 → 4. 新建商品（名称、短名、价格、徽标、周期、限购、下单须知、主图/多图/视频）→ 5. 上架（新建默认下架，避免误上架）→ 6. 需要调整归属时用"批量移动到分部"（只改归属，不改名称与价格；整批校验，缺一个整批回滚）→ 7. 客户端的目录、价格与图片随缓存策略在 60 秒内更新（回到前台或下拉刷新立即强制拉取）。

### 4.9 版本发布流程（管理端 + 发布脚本）

1. 构建客户端安装包（注入版本码、版本名与服务器地址）；2. 通过发布脚本上传到对应通道（老板端 / 工作端）；3. 服务端校验文件为 APK、计算 sha256、拒绝重复版本码、自动停用旧版本；4. 客户端启动时检测更新 → 弹出更新说明（普通可稍后 / 强制则阻断）→ 下载（进度显示）→ sha256 校验 → 调用系统安装；5. 发布后独立复核云端"最新版本"接口与实际安装包一致。

## 第五章 技术特点

### 5.1 架构特点

| 特点 | 说明 |
|---|---|
| 三端一后端 | Flutter 双端 + Vue3 管理端共用一套 NestJS 服务端；业务规则只实现一次，客户端只做展示与交互 |
| 客户端不可信 | 价格、积分、身份、订单状态全部以服务端为准；主体 ID 只从令牌载荷取，绝不信任请求体或路径参数中的用户标识 |
| 数据模型可扩展 | 游戏/分部/分类/商品/价格/图片/视频全部后台配置；新增游戏原则上零客户端改动 |
| 迁移可控 | 数据库表结构只通过迁移脚本变更（55 个迁移文件），关闭 ORM 自动同步，避免结构漂移 |
| 依赖边界清晰 | 共享 Dart 包 `fish_core` 统一设计 token、接口客户端与模型，双端复用 |
| 开源合规 | 只引入宽松许可（MIT / Apache-2.0 / BSD）依赖；GPL/AGPL 类仅作内部参考，不引入依赖，不复制第三方素材 |

### 5.2 安全特点

| 机制 | 说明 |
|---|---|
| 登录与会话 | 口令 bcrypt 哈希；访问令牌 2 小时、刷新令牌 30 天轮换；同账号**单设备登录**（再次登录即顶号，原会话失效）；登出与改密码即吊销会话 |
| 受限会话 | 打手态（伴随会话）与 App 内"管理员身份"（充值受限会话）都是**允许清单制**的受限会话：只放行明确列出的接口，其余一律 403；将来新增接口默认对受限会话关闭 |
| 每请求校验 | 受限会话的有效性每次请求实时查库（无缓存）：绑定是否仍有效、账号是否被封禁、档案是否在职；解绑/封禁后已建立的实时连接被主动断开 |
| 并发正确性 | 抢单、派单确认、结算、发放、客服接入一律用**条件更新判影响行数**或数据库唯一约束，禁止用缓存锁形成双数据源 |
| 幂等 | 下单、发放、充值申请、消息发送、绑定等写操作均带幂等键并落库唯一约束，重复提交不产生第二笔业务 |
| 审计留痕 | 管理员每一个改变数据的动作写操作日志（请求摘要只记关键字段，不记口令/令牌/超长原文）；登录与身份变更写登录日志；订单每次状态变化写状态日志 |
| 资金安全 | 平台不经手资金、无支付通道、无提现；充值由人工审核后手工发放；积分流水只增不删、前后余额快照可对账 |
| 配置安全 | 高安全配置项标记为"仅超管可写"，服务端统一在配置服务的一处收口校验，读侧实时读库；配置变更写操作日志 |
| 内容与素材 | 界面图标统一使用内置线性图标；不使用第三方 App 的图片、插画、吉祥物与文案 |

### 5.3 实时通信特点

| 特点 | 说明 |
|---|---|
| 通道 | Socket.IO（WebSocket）长连接，路径 `/ws/chat`；连接握手即校验令牌与会话有效性 |
| 房间模型 | 按会话房间与用户房间分发；加入会话前校验成员身份；受限会话在握手阶段即按规则放行或拒绝 |
| 消息可靠性 | 发送携带客户端消息 ID（幂等）；同一会话内消息按服务端分配的序号排列；历史消息走接口分页拉取 |
| 已读机制 | 服务端保存双方已读位点，客户端展示单勾（已送达）与双勾（已读） |
| 实时事件 | 新消息、未读同步、撤回、订单状态变化、派单通知、客服接入与释放、充值到账通知等 |
| 心跳与失效 | 心跳周期校验会话有效性；受限会话被释放或封禁时，服务端主动断开其连接（实测断开耗时 27–28 毫秒） |
| 客户端稳定性 | 实时连接在客户端为全局单例，避免重复连接；断线重连后自动补拉未读 |

## 附录 A 术语表

| 术语 | 含义 |
|---|---|
| 老板 / 老板态 | 下单用户的俗称；老板在 App 内的默认身份态 |
| 打手 / 打手态 | 为老板提供陪玩代练服务的工作人员；老板端 App 内可切换的第二态 |
| 分部 | 游戏 + 平台（端游/手游）的组合，是目录与接单权限的基本单位 |
| 抢单 / 派单 | 订单进入大厅由打手先到先得领取；或由管理员指定打手并等待其确认 |
| 结算 | 订单完成后按后台配置的抽成比例把订单金额分给打手与平台，并写流水 |
| 伴随会话 | 老板切换到打手态时签发的受限会话，只顶掉伴随会话，不影响打手本人的登录 |
| 受限会话 | 只允许访问明确列出的接口的会话；默认拒绝其余全部接口 |
| 抽成比例 | 平台从订单金额中抽取的百分比（整数，后台可配，默认 25%，范围 0–50） |
| 幂等键 | 写操作携带的唯一键，用于保证同一次业务提交只生效一次 |
