pointsPerYuan：前端默认值 10，服务端现值 1

前端在 api/recharge.ts 里把「1 元到账多少余额」的兜底默认值写成了 10， 而服务端常量与库中现值都是 1。正常路径下前端会用接口下发值覆盖它， 所以平时看不出来；一旦配置接口没拿到值，管理端就会按 10 倍换算并显示。 本图只出方案，不改代码。

前端默认：10（api/recharge.ts:150） 服务端默认：1（recharge-config.ts:99） 库中现值：1 差额：10 倍

两个数字

admin-web/src/api/recharge.ts:150
10
前端兜底默认值
DEFAULT_POINTS_PER_YUAN = 10
≠
server/…/recharge-config.ts:99
1
服务端默认值 = 库中现值
pointsPerYuan: 1（1 元 = 1 元）

这个不一致会导致什么

触发条件 配置接口没拿到值时 → 管理端按 10 倍换算并显示 RechargeView
① 正常路径（没事）：进页面 → loadConfig() 成功 → Object.assign(draft, { pointsPerYuan: cfg.pointsPerYuan }) → 草稿被服务端的 1 覆盖 → 显示正确。
② 异常路径（出事）：getConfig() 失败（网络抖动 / 500 / 会话中途丢权限 403）→ catch 只弹一句报错，saved 仍为 null、draft 保持初值 → draft.pointsPerYuan 停在字面量 10 → 页面照常渲染这块面板。
③ 同源第二处：即使请求成功，只要服务端响应里缺 pointsPerYuan 键， normalizeConfig() 也会回落到 DEFAULT_CONFIG.pointsPerYuan = 10 —— 兜底兜的是错的那个数。
✓ 一个缓解因素（必须说清）：cfgDirty 在 saved === null 时返回 false， 于是「保存设置」按钮处于禁用态 → 这个错误数字写不进库。 所以本项是显示误导，不是数据损坏。（但误导的是超管，后果仍不可小看 —— 见右。）

到账比例

老板端每一档显示多少余额、审核列表里的「应得余额」，都由这一项算出来（口径：余额 = 元，1 元 = 1 元）。
1 元 到账 10余额 例：付款 10 元 → 到账 ¥100.00 · 付款 68 元 → 到账 ¥680.00
改这里会影响全站口径：老板端「充值」页显示的应得余额、各档位到账余额、审核列表的应得余额， 全部按「1 元 到账 10 余额」实时计算。改动立即生效，请先跟负责人确认新口径再保存。
保存设置 重置为当前生效值 （禁用：草稿未加载，无"当前生效值"可比）
⚠ 为什么这不是"小事"：这块面板是全站资金口径的唯一配置入口，而它现在把 ¥10.00 说成 ¥100.00（previewPoints 直接乘 draft.pointsPerYuan）。 超管看到"付款 10 元到账 100 元"的第一反应可能是去改这个数字（以为线上真的配成了 10）—— 一旦他把 10 改成别的值并保存，就真的改了全站口径。
// ① 前端把兜底默认值写成 10（api/recharge.ts:149-163） export const DEFAULT_AMOUNT_OPTIONS = [6, 10, 20, 38, 68, 98, 128, 198, 328, 648]; export const DEFAULT_POINTS_PER_YUAN = 10; // ← 服务端是 1 export const DEFAULT_CONFIG: RechargeConfig = { amountOptions: [...DEFAULT_AMOUNT_OPTIONS], minYuan: 1, maxYuan: 9999, // ← 服务端默认是 10000，也不是同一个数 pointsPerYuan: DEFAULT_POINTS_PER_YUAN, … }; // ② normalizeConfig 用它兜底（:177） pointsPerYuan: asNum(pick(r, ['pointsPerYuan', 'points_per_yuan']), DEFAULT_CONFIG.pointsPerYuan), // ← 缺字段就变 10 // ③ 页面草稿又是一份字面量（RechargeView.vue:1017-1029） const draft = reactive<RechargeConfig>({ amountOptions: [], customEnabled: true, minYuan: 1, maxYuan: 9999, pointsPerYuan: 10, // ← 第三份字面量，与上面两处各写一遍 pendingLimitPerUser: 3, adminLimit: 5, … }); // ④ 预览直接乘它（:1059-1062 → 模板 :228） function previewPoints(yuan) { return (draft.pointsPerYuan ?? 0) * yuan; } 例：付款 10 元 → 到账 {{ formatYuan(previewPoints(10)) }} // 10 × 10 = ¥100.00（真值 ¥10.00）

两种改法

改法 A 前端不写默认值，一律用接口下发值 推荐
// ① api/recharge.ts：删掉这个常量，类型改可空 export const DEFAULT_POINTS_PER_YUAN = 10; // ← 删除 interface RechargeConfig { /** 1 元到账多少余额（**只认服务端下发值**；未取到 = null，不编造） */ pointsPerYuan: number | null; … } // ② normalizeConfig：缺字段 → null（而不是回落到一个猜的数） pointsPerYuan: pick(r, ['pointsPerYuan', 'points_per_yuan']) == null ? null : asNum(pick(r, ['pointsPerYuan', 'points_per_yuan']), null), // ③ 页面草稿同样不写数字 const draft = reactive<RechargeConfig>({ …, pointsPerYuan: null, … }); // ④ 预览：没拿到值就**明说没拿到**，不显示一个假的金额 function previewPoints(yuan: number): string | null { if (draft.pointsPerYuan == null) return null; return String(draft.pointsPerYuan * yuan); } // 模板 <template v-if="previewPoints(10) !== null">例：付款 10 元 → 到账 {{ … }}</template> <template v-else>未取到服务端配置，比例以服务端下发为准</template>
为什么推荐「1 元到账多少余额」是服务端权威口径（存 system_setting、仅超管可改、读侧实时读库）。前端没有资格猜一个兜底值 —— 猜对没好处，猜错就把 ¥10 说成 ¥100。
顺带收口同一文件里 maxYuan: 9999 与服务端默认 10000 也不一致 → 一并按"未取到 = null"处理（不再编造上下限）。
影响面不需要动服务端。只改 admin-web/src/api/recharge.ts 与 views/RechargeView.vue；vue-tsc 会把所有用到该字段的地方标出来（可空类型的好处）。
改法 B 默认与后端常量同源 把 10 改成 1
// admin-web/src/api/recharge.ts:150 // ⚠ 与 server/src/modules/recharge/recharge-config.ts:99 的 // RECHARGE_CONFIG_DEFAULT.pointsPerYuan 必须一致（改一处要改两处） export const DEFAULT_POINTS_PER_YUAN = 1;
做法把前端默认值从 10 改成 1，与 recharge-config.ts:99 对齐。
好处改动最小（一个字符）；今天两个数就一致了。
为什么次选仓库里 admin-web 与 server 是两个独立 package（根 package.json 没有 workspaces，没有共享常量包）→ 这个"同源"只能靠注释与自觉维持，没有任何机制阻止它们再次漂移。而这次漂移的根因正是"同一个业务常量在两地各写一遍"。
另外它没解决 maxYuan: 9999 vs 10000 那处同类不一致。

同类不一致一并清点（同一根因）

✓ 对照组：客户端做对了。老板端 core 的 RechargeConfig 把该字段默认成 0，并用 effectivePointsPerYuan => pointsPerYuan > 0 ? pointsPerYuan : 1 兜底； 且 recharge_page.dart 明确不拿它做换算。也就是说"不编造数字"这个口径， 客户端已经这么做了 —— 管理端是唯一还在猜的地方。

逐项口径

项内容
现状前端 api/recharge.ts:150 的 DEFAULT_POINTS_PER_YUAN = 10 与 RechargeView.vue:1022 的草稿字面量 10，都与服务端 recharge-config.ts:99 的默认值 1（= 库中现值）不一致，差 10 倍。正常路径下 loadConfig() 会用接口值覆盖草稿，所以平时不显形；一旦 getConfig() 失败（网络 / 500 / 中途丢权限 403），草稿就停在 10，管理端「到账比例」面板会显示 1 元 到账 10 余额，并把 付款 10 元 → 到账 ¥100.00（真值 ¥10.00）算给超管看。
缓解因素：cfgDirty 在 saved===null 时为 false → 保存按钮禁用 → 错误值写不进库，属显示误导而非数据损坏。
同类第二处：maxYuan 前端 9999 vs 服务端 10000。
建议改法 A（推荐）：① api/recharge.ts 删除 DEFAULT_POINTS_PER_YUAN，把 pointsPerYuan（以及 maxYuan）类型改为 number | null；② normalizeConfig() 对缺失字段返回 null 而不是回落到一个猜的默认值；③ RechargeView.vue 草稿初值同步改 null；④ previewPoints() 在 null 时返回 null，模板改为显示「未取到服务端配置，比例以服务端下发为准」而不是一个假金额；⑤ 输入框在 null 时显示占位符而非数字。
改法 B（次选）：仅把前端默认值改成 1 —— 改动最小，但"两地各写一遍"的结构没变，没有机制阻止再次漂移。
影响面改法 A：不需要动服务端（只改 admin-web 两个文件）。
改法 B：也不需要动服务端（改 1 个字符）。
两种改法都不改接口、不改数据结构、不改数据库。若将来想让"同源"真正有机制保障，可考虑建一个共享常量包 —— 那是架构级改动，不在本方案范围，仅作备注。
红线docs/14：否。不改任何视觉决策；唯一可见变化是"配置没取到时显示一句说明"而不是一个错误数字 —— 属内容正确性。
docs/21：否，且正向合规。§三「内容层」明文禁止"编造的装饰数据"、"只展示系统真实产生的数据；没有就留空态" —— 前端凭空把 1 说成 10、把 ¥10.00 说成 ¥100.00，正是这条禁止的"编造数据"。
