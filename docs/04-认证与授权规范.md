# 04 - 认证与授权规范

## 账号模型

- 统一账号表 `user`，`role` 区分：user（老板）/ worker（工作端）/ admin（管理员）
- 老板端用户可自助注册（账号密码）；工作端账号由管理员后台创建；管理员账号由超级管理员创建
- 登录接口按 `role` 分流校验：请求 role 与实际账号 role 不符返回 403
- **登录限流返回 429（2026-10-13 统一）**：`/auth/login` 与 `/auth/qq/login` 超限（**5 次/分/IP+账号**）
  一律 **429 + 中文「登录尝试过于频繁，请稍后再试」**（此前是 403，与同平台其余限流点分裂；现已按
  docs/03 第 35 行「429 = 触发限流」统一）。
  ⚠️ **与「账号角色不符」的 403 严格区分**（上一条）：两者同文件、原本同为 `ForbiddenException`，
  **只靠文案区分** —— 「登录尝试过于频繁，请稍后再试」= 429 限流／「账号角色不符」= 403 越权。
  **禁止把"角色不符"一起改成 429**（会把越权判定降级成"稍后重试"）。
  回归两条一起断言：`scripts/tmp/security-test.js` 第 7 条（429 + 文案）与第 7b 条（角色不符仍 403）。

## JWT

- access token 有效期 2 小时（开发期），refresh token 30 天（轮换制：每次刷新吊销旧 jti）
- payload：`sub`（user.id）、`role`、`jti`、`type`（access/refresh）
- 签发后写入 auth_token 表；登出/踢下线/轮换即置 revoked；守卫校验 revoked
- 密钥 JWT_ACCESS_SECRET / JWT_REFRESH_SECRET 来自环境变量

| 守卫 | 职责 |

### 决策修订（负责人 2026-10-03）

- **运营角色（operator）实际持有 `admin:worker:permission`**（可授予/取消打手的接单、客服权限），负责人确认**维持现状**——运营需要按业务开通打手权限。
- 运营角色可持有并使用该权限点；具体哪些角色持有由超管在「管理员与角色」页配置，服务端只校验权限点，不额外硬编码"仅超管"。
- 仍为超管专属（运营/普通管理员无）：`admin:wallet:grant`（积分发放/回收）、`admin:user:level`、`admin:user:ban`、`admin:user:delete`、`admin:role:write`、`admin:admin:write`、`admin:setting:write`、`admin:leaderboard:adjust`、`admin:order:cancel`。
- 授权/取消授权限全程写 operation_log（含变更前后值），可审计。

## 服务端校验规则（任何接口不得绕过）

1. 主体 id 只从 JWT `sub` 取；请求参数中的 userId/workerId/管理员 id 一律不可信
2. 资源归属校验：`GET /user/orders/:id` 必须 `WHERE id=:id AND user_id=当前主体`，伪造他人 id 返回 403
3. worker 能力校验：接单接口 = role=worker 且实时查库 `can_take_order=1` 且在职；客服接口同理 `can_serve_customer=1` 且会话在 chat_conversation_assign 有 active 授权
4. 管理员接口 = PermissionGuard 校验权限点；超级管理员内置放行
5. 所有拒绝（403）写安全审计（attempt 记录）

## 越权自测用例（每个新模块必须跑一遍）

- 普通用户 token 调用管理员接口 → 403
- 工作端伪造 workerId 接他人订单 → 403
- 用户伪造 userId 查他人订单/会话 → 403
- 修改订单 ID/商品 ID/价格/积分/权限/状态参数 → 无效且 4xx
- 重复请求（同幂等键）→ 返回首次结果；请求重放（旧 token/旧请求ID）→ 拒绝

## 补充（2026-09-21）：单账号单设备会话

- 原则：一个账号同时只允许一个有效会话；**后端强制执行**（JwtAuthGuard + WS 网关双重校验），前端仅做提示
- `auth_token.revoked` 语义扩展：0 有效 / 1 已登出或轮换失效 / 2 被新设备登录顶掉
- 登录签发新令牌对前：`UPDATE auth_token SET revoked=2 WHERE user_id=? AND revoked=0`（旧端所有令牌立即失效）
  - **⚠️ 精度补充（2026-10-06）**：该语句实际带 `AND kind='primary'` 过滤 —— **只顶 primary，不顶 companion**。
    **「primary 之间仍互斥」这条铁律本身没有变化**（只存在 primary 时过滤条件恒真）；原因与补偿约束见文末「伴随会话」一节。
- 守卫：revoked=2 → 401「账号已在其他设备登录」；revoked=1/不存在 → 401「登录已失效，请重新登录」
- refresh：先条件更新 `UPDATE ... WHERE id=? AND revoked=0` 判 affectedRows（防竞态误伤新会话），revoked=2 时拒绝并提示被顶
- WS：握手时校验会话登记；应用层 ping 心跳每次重校验，被顶/登出后 emit `auth:session-replaced` / `auth:expired` 并断开
- 客户端：API 401 被顶文案或 WS 踢出事件 → 全局清本地会话 + 弹窗「登录状态变更」→ 登录页（Flutter core SessionKickListener / admin-web 跳 /login?reason=）
- 权限点新增：`admin:user:level`（用户等级调整，默认仅超管，仅限老板端）、`admin:user:ban`（用户封禁/解封）、`admin:user:delete`（用户删除）、`admin:forum:moderate`（论坛内容管理）
  - ⚠️ **`admin:forum:moderate` 已失效（2026-10-05）**：玩家圈整体下线，该权限点随论坛模块一并失去用途（保留历史记录，**不再授予/不参与鉴权**）
- 封禁（2026-09-22）：封禁即吊销该账号全部会话；到期后首次登录自动解封；被封登录返回 403 errorCode=ACCOUNT_BANNED（客户端弹窗展示封禁结束时间）；admin 角色账号不可被封禁/删除

## 补充（2026-10-06）：伴随会话（companion）——一 App 双态的身份切换

负责人定案（方案甲「一 App 双态」）：老板端内用**打手账密**切换到打手态时，签发的是 `kind=companion` 的**受限会话**。
它必须"能用打手侧接口"，又必须"绝不能被当成 primary 用"。数据模型与结构规则见 CLAUDE.md 结构规则 11；表结构见 docs/02。

### kind 语义（`auth_token.kind`）

| kind | 来源 | 顶号范围 | TTL | 用途 |
|---|---|---|---|---|
| `primary` | `POST /auth/login` 及 `refresh` 轮换 | 只顶该账号其它 **primary**（`revoked=2` + 原文案） | access 2h / refresh 30 天 | 老板态 / 工作端 / 管理端的正常登录 |
| `companion` | `POST /user/identity/bind`（或 `POST /user/identity/refresh` 续期） | **只顶该账号其它 companion**（`revoked=1`），**绝不触碰 primary** | **access 12h 且 refresh 12h**（硬上限） | 老板端内的打手态 |

- 存量 `auth_token` 行迁移时一律落 `primary`（migration `1802000000000-auth-token-kind`）→ **单设备登录语义逐字节不变**
- `companion` 的 `binding_id` 指向 `worker_identity_binding.id`（primary 为 `NULL`）
- **会话种类以库中登记为准（`auth_token.kind`），令牌载荷里的 `kind/bindingId` 只作观测与客户端分流，不参与任何判定**（载荷可被伪造，库不可）

### 与单设备登录的关系（⚠️ 最容易被误读的一条）

- **primary ↔ primary 仍严格互斥，单设备铁律未豁免、未削弱。** 同账号在新设备登录依旧把旧的 primary 置 `revoked=2`（旧端 401「账号已在其他设备登录」）。
- 唯一变化：primary 的吊销语句加了 `kind='primary'` 过滤 —— **在只存在 primary 的世界里该条件恒真，与历史逐字节等价**（`session-test.js` 13/0 钉死）。
- 为什么必须加这个过滤：打手手机上可能仍装着旧版工作端 App，其 primary 会话每 2 小时续期一次；若 primary 续期把 companion 一起顶掉，老板的打手态会被**每 2 小时踢一次**。
- companion 侧的等效约束由**三重限制**补偿：**12h 硬 TTL** + **每请求校验绑定有效** + **解绑即刻全量吊销**。

### 签发 / 吊销

- **签发**：`POST /user/identity/bind`（老板侧，`@Roles('user')`）校验打手账密 → 建/复用绑定 → `issueCompanionTokens()`。
  返回 `companionToken` / `companionRefreshToken` / `companionExpiresIn`，并明确 `bossTokenUnchanged: true`（**老板自己的 token 不变**）。
  已绑给自己时**直接复用绑定并重新签发**（换机 / 12h 过期后再切换的正常路径，属预期行为）。
- **续期**：`POST /user/identity/refresh`（**公开接口**，**只吃 companion 的 refreshToken**，不需要也不应持有老板 token）；
  续期仍走 `AuthService.refresh` 的轮换逻辑：校验绑定仍 `active`、**只顶 companion**、TTL **仍 12h**（不会把 12h 续成 30 天）。
  - **kind 闸门（安全审计 F5）**：库中登记不是 `companion` 的令牌（含老板 **primary** 的 refreshToken）一律
    **401「该令牌不是伴随身份，请使用 /auth/refresh」**，且该判断在**任何写操作之前** —— 旧实现会把 primary 的
    refreshToken 当伴随会话续期，顺带走 primary 轮换分支把该账号**正在使用的 primary 会话吊销掉**（实测原 token 立刻 401）。
- **吊销**：
  - `POST /user/identity/unbind` → 绑定置 `unbound` **并立即按 `binding_id` 批量吊销该绑定的全部 companion 会话**（access + refresh），打手态下一次请求即 401，
    并**主动断开**这些会话的 WS 连接（不等心跳）+ 写 identity 审计（见下文「释放路径的四个动作」）；
  - 打手停用 / 封禁 / 删除账号触发的**系统释放**走同一实现（同一条 SQL、同一吊销、同一审计、同一断线）；
  - companion 被同账号的新 companion 顶掉 → `revoked=1`（文案「伴随身份已失效，请重新绑定打手账号」）；
  - 登出 `POST /auth/logout`、refresh 轮换 → 按既有规则置 `revoked=1`。

### 登出必须同时吊销 access 与 refresh（同一次登录的全部令牌，2026-10-07 定案）

> **一句话规则**：`POST /auth/logout` 必须把**这一次登录在 `auth_token` 里的全部行（access + refresh）
> 一次性吊销** —— 「登出」的语义是"这次会话彻底结束"，**不是**"只让手里的 access 失效"。

**为什么单列一条**：旧实现只吊销"调用方给的那几个 jti"（`accessJti` 恒吊销；`refreshToken` 是
`LogoutDto` 的**可选**字段，不传就什么都不做）。于是**登出干不干净取决于客户端传没传 refreshToken**，
而只带 access 调用的路径（自证脚本、第三方集成、任何漏传的客户端）会留下 `revoked=0` 的 refresh 行：
实测残留一行 `kind='recharge'`、TTL 还剩 3.9 小时 → **已"退出登录"的会话仍能用它换到新的 access**，
等于没退。

**配对关系怎么定（不改表结构）**：`auth_token` 没有 `family_id`/`session_id` 这类族标识，
而 `created_at` 时间窗**覆盖不全**（中间调过一次 `POST /auth/refresh` 轮换，新 refresh 行的
`created_at` 就跑到几小时后，登出时配对不上）。因此按 **`user_id + kind`** 收口：
三类会话在本平台**各自都只有一条活会话**（`issueTokens` 每次签发都会先把"同账号同族"的未吊销行置 1），
所以"该账号该族的活行集合"**恒等于**"这一次登录的那一对"，吊销它 = 精确吊销本次登录的全部令牌。

**语义边界（一条都不能松）**：

1. **只吊销自己**：`WHERE user_id = 会话登记主体 AND kind = 本会话的 kind`；
   `userId` 由守卫从**库中登记行**取出（`request.user.userId`），`kind` 同样取自库中 access 行
   —— **从不信任令牌载荷或请求体**。
2. **绝不影响其它 kind**：`companion` 登出**绝不动 primary**（老板在管理端/老板态的登录照常），
   `recharge` 同理；反过来老板 primary 登出也不动同账号的 companion（硬要求，有用例钉死）。
3. **不带他人令牌下线**：请求体里带来的 `refreshToken` 只有在"**该行存在 + 属于本次登出的账号 + kind 相同**"
   时才被吊销 —— 防止"拿别人的 refresh 打我的登出"把别人踢下线。
4. **primary ↔ primary 互斥铁律不变**：那是 `issueTokens()`（登录/续期顶号置 `revoked=2`）的职责；
   登出**不做任何跨会话判定**，它只是把"同一族的活行"收干净。
5. **WS 一并断开**：登出返回被吊销的 jti 列表，控制器交给 `RealtimeGateway.disconnectByJti()`
   （只改库不踢线 = 旧连接继续收消息，与安全审计 F1 同一类根因）。

**三类会话同规则**：`primary`（老板端/工作端/管理端）、`companion`（打手态）、`recharge`（App 内受限管理态）
走**同一个实现**（`AuthService.logout`）；companion/recharge 的续期通道字段名不同，但登出这条路径完全一致。
客户端侧同样要**把两族受限会话各自注销**（`POST /auth/logout` 在两份接口族白名单里都放行）：
只清本地令牌 = 服务端那两族仍活到 12h TTL 到期。

**回归**：`scripts/tmp/logout-revoke-test.js`（三类会话各自的 access 401 / **refresh 401** / 该族活行为 0，
外加"companion 登出不影响 primary"与"跨账号 refresh 踢不动人"的负向断言）。

### 每请求校验（companion 专属，无缓存，每次请求一条 SQL）

> **实现只有一份（安全审计 F1-a，2026-10-06）**：`server/src/modules/auth/companion-session.check.ts` 的
> `checkCompanionSession()` —— **HTTP 守卫（每请求）与 WS 网关（握手 + 心跳）共用**。
> 旧实现只有 HTTP 守卫有这套校验，WS 侧只看 `auth_token.revoked` → 实测「HTTP 已 401（绑定已释放/老板已封禁），
> **旧 WS 连接仍能 join 房间并继续收到 `msg:new` 全文**，同一令牌还能新建连接」。
> 不允许在网关里复制第二份 SQL（复制出来的第二份迟早与守卫分叉，这正是本次漏洞的根因）。

依次校验，任一不满足 → **401 + 中文**（客户端据此退出打手态）：

1. `auth_token.kind='companion'` 且 `binding_id` 非空；
2. 绑定行存在且 `status='active'`（**解绑即刻失效**）；
3. 绑定里的 `worker_user_id` **必须等于会话主体**（防绑定 id 与主体错配）；
4. 打手账号**未被封禁**（`user.status=1`）→ 否则 401「该打手账号已被封禁，伴随身份不可用」；
5. 打手档案**在职**（`worker.status=1`）→ 否则 401「该打手账号已停用，伴随身份不可用」；
6. **老板账号未被封禁且仍存在**（`boss_user_id` → `user.status=1`，2026-10-06 缺口 1 **双保险**）→ 否则 401
   「老板账号已被封禁，伴随身份已失效，请重新登录老板账号」。正常路径下封禁/删除已把绑定置 `unbound`
   （第 2 条先命中），这一条专门兜住**历史悬空 active 行**（本次修复前留下的行、或将来某个入口忘了释放）。

### 接口族白名单（**默认拒绝**）

companion **只**能访问下表接口；**其余一律 403 + 中文**「伴随身份无此操作权限，请切回老板身份后操作」。

| 可访问 | 路径 | 说明 |
|---|---|---|
| 打手族 | `/worker/*` | 大厅 / 抢单 / 派单确认 / 开始 / 提交 / 我的订单 / 收益 / 待遇 / 客服会话 / 排行榜 |
| 消息族 | `/user/conversation*`、`/user/conversations*` | 客服会话与「老板 ↔ 打手」一对一直聊的列表 / 历史 / 发送 / **一键已读**（按 `type` 分区）。**含 `POST /user/conversations/:id/read`**（2026-10-06 缺口 3 新增的 REST 一键已读；由该前缀规则一并放行，打手态也要能一键已读） |
| 好友（**仅两条**） | `GET /user/friends`、`POST /user/friends/:id/conversation` | 好友列表（**读**）与「打开已有好友会话」；服务端只认 `accepted` 关系，**不可能借此建立新好友关系** |
| 资料读 | `GET /user/profile`、`GET /user/profile/*` | 聊天里点头像看公开资料 |
| 媒体 | `/media/*` | 聊天图片上传与受保护读取 |
| 会话自身 | `GET /auth/me`、`POST /auth/logout`、`POST /auth/refresh` | 我是谁 / 登出 / 续期 |

**明确不可访问**（403 中文）：`/user/identity/*`（绑定管理＝老板侧能力，否则打手态可自行解绑/换绑）、`/auth/password`（改密码）、
`PUT /user/profile` 与 `POST /user/profile/uid`（改资料/改 ID）、`/user/orders`（下单）、`/user/wallet`、`/user/tips`、`/user/refunds`、
`/user/complaints`、`/user/ai/*`、`/user/notifications*`、`/user/friends*` 里除上述两条外的全部路由（搜索 / 申请 / 同意 / 拒绝 / 删除）、`/admin/*`。

- 这是**允许清单（allow-list）而不是黑名单**：**将来新增接口默认对 companion 关闭**，必须显式加进 `isCompanionAllowedRoute` 才能用。
  黑名单模式会在"新接口忘了加规则"时静默放开，这是不可接受的默认值。
- 路由前缀变更安全：判定前会剥掉 `/api/v\d+` 前缀再比对，因此 `/api/v2` 之类不会让白名单静默失效。

### 封禁 / 删除即释放绑定（**对称**）

负责人 2026-10-06 裁决（**缺口 1 / 缺口 2 收尾**）——释放必须**对称**，因为同一账号既可能是打手（被绑的一方），
也可能是老板（绑定别人、持有 companion 的一方）：

| 入口 | 释放范围 | 代码位置 | 响应回带 |
|---|---|---|---|
| `POST /admin/users/:id/ban`（封禁账号） | **两侧**：`worker_user_id = 该账号` ∪ `boss_user_id = 该账号` | `UserAdminService.ban` → `BindingReleaseService.releaseBoth` | `releasedBindings`（总数）+ `releasedAsWorker` + `releasedAsBoss` |
| `DELETE /admin/users/:id`（删除账号） | **同上（既有事务内，提交后再断开 WS）** | `UserAdminService.deleteUser` → `BindingReleaseService.releaseBothInTx` | 同上 |
| `PUT /admin/workers/:id`、`PUT /admin/workers/:id/players-profile`（停用打手档案） | 打手侧（既有行为不变） | `worker-admin.service.ts` → `BindingReleaseService.releaseWorkerSide` | `releasedBindings` |
| `POST /user/identity/unbind`（老板**主动**解绑） | 指定的那一条绑定 | `WorkerIdentityService.unbind` → `BindingReleaseService.releaseBinding` | `revokedSessions` |

**⚠️ `auth_token.user_id` 的归属（安全审计 F1-c：纠正一条写反了的注释）**：
companion 会话行的 `user_id` 是**打手**账号（`auth_token.user_id = 打手 user_id`，`kind='companion'`，另带 `binding_id`），
**不是**老板。因此 `ban()` 里那条 `UPDATE auth_token SET revoked=1 WHERE user_id = 被封账号`：
- 封**打手**时命中它自己的 primary + companion（本来就该全吊销）；
- 封**老板**时**扫不到**老板名下那条 companion —— 必须靠**按 `binding_id`** 的吊销兜住（`releaseBindings()` 的第 3 步，已实现并实测）。
旧注释写「companion 会话同属该 user_id，一并被吊销」与事实相反，已删除；**不要**再按那个假设写代码。

#### 释放路径的四个动作（安全审计 F1-b / F4 收口，唯一实现 `worker-binding-release.ts` 的 `releaseBindings()`）

任何释放路径（主动解绑 / 打手停用 / 封禁 / 删除）一次调用内**同步**做完四件事，调用方没有机会漏掉任何一步
（`BindingReleaseService` 是唯一入口）：

1. **置 `unbound`**：`WHERE id IN (...) AND status='active'`（只动 active 行，历史行与 `unbound_at` 一律保留）；
2. **按 `binding_id` 吊销该绑定的 companion 会话**：`SET revoked=1 WHERE binding_id IN (...) AND kind='companion' AND revoked=0`
   （与"老板主动解绑"同一语义；旧实现只在主动解绑一条路径上做，其余三条路径连令牌都不吊销）；
3. **主动断开这些会话的 WS 连接**：`RealtimeGateway.disconnectByJti()`（先发 `auth:expired` 再 `disconnect(true)`，
   实测 HTTP 请求后 **27–28ms** 内断开），不等下一次心跳；删除账号走事务，**提交成功后**才断开（回滚不该踢线）；
4. **写持久化审计**（见下）。

#### 解绑审计（安全审计 F4：解绑必须留痕）

写 **`login_log`**（`user_type='identity'`，与"绑定"同一口径；**不是** `operation_log` —— 后者没有 UA 列，
且管理端封禁/删除那一下已经在它里面留了"管理员动作"那一行，身份事件写进去只会把绑定生命周期拆到两张表）：

| 列 | 内容 |
|---|---|
| `user_id` / `username` | **老板**（绑定属主）的 id / 登录名 —— 该伴随会话的归属方 |
| `ip` / `user_agent` | 触发请求的 IP / UA（主动解绑=老板设备；系统释放=管理员请求） |
| `result` | `success` |
| `fail_reason` | `解绑：<来源> \| binding=<id> \| boss=<id> \| worker=<id> \| by=<触发者>` |
| `created_at` | 释放时刻 |

来源四种取值（可 grep）：`老板主动解绑` / `系统释放（打手档案停用）` / `系统释放（封禁账号）` / `系统释放（删除账号）`；
触发者 `by=`：`user:<boss id>(<登录名>)` 或 `admin:<管理员 user id>`（无触发者时 `system`）。
审计行数与释放行数一一对应（没有 active 行时**零写入**，幂等）。

- **历史行一律保留**：只把 `status='active'` 的行置 `unbound` + 写 `unbound_at`，**不物理删除**（可审计）；
  唯一键建在生成列上（非 active 为 NULL）→ 释放后**名额自动让出**，可重新绑定。
- **缺口 1（封禁老板）**：旧实现只释放打手侧 → 老板被封禁后其名下 companion **仍然可用**（实测 `ban releasedBindings=0`、
  companion `200 → 200`）。修复后：companion 依赖的绑定立即 `unbound` → 下一次请求 **401 中文**
  （「伴随身份已失效，请重新绑定打手账号」），且**解封不自动恢复**（`unban` 只回写 `user.status=1`，需老板重新输打手账密绑定）。
- **缺口 2（删除账号）**：旧实现完全不释放 → 悬空 `active` 行让老板侧 `GET /user/identity` 报 **400「打手档案不存在」**
  且名额被永久占住（无法再绑）。修复后在**同一事务内**释放两侧 → `GET /user/identity` 回 **200 + `bound:false`**，
  名额可被**其他老板立即重新绑定**（实测）。
- 守卫侧的老板账号校验（上文「每请求校验」第 6 条）是**双保险**：即使出现历史悬空 active 行，companion 也一律 401。
- **WS 侧同样生效（安全审计 F1）**：绑定释放/封禁后，同一令牌**新建 WS 被拒**、**已连接的 WS 被主动断开**
  （实测 HTTP 请求后 27–28ms 收到 `auth:expired` + `disconnect`），且**打手 primary 完全不受影响**（HTTP 200 + 其 WS 连接保持）。

### 其它安全审计修复（2026-10-06，低危但已全部修掉）

- **F2 账号枚举**：`POST /user/identity/bind` 的"账号不存在"与"密码错"**必须逐字同一句**「账号或密码错误」
  （与 `/auth/login` 同口径）。旧实现分开写「账号不存在或密码错误」/「账号或密码错误」，两个字的差异就足以批量判定
  某登录名是否注册（绑定限流按 `IP+账号` 分桶，换账号即可继续探测）。
- **F3 会话存在性 oracle**：`POST /user/conversations/:id/read` 的**非当事方**一律 **404「会话不存在」**
  （与 `GET /user/conversations/:id/messages` 同口径）。旧实现对 worker 角色调用者直接走 `assertWorkerCs` →
  **403「无该会话客服授权」**，而"会话不存在"是 404 → 自增会话 id 的 404/403 分布 = 平台上存在哪些会话。
  **当事方的正当 403 语义保留**：被指派客服若被撤了客服权限，仍 403「无客服权限」（判定在 `assertWorkerCs`）。

### 绑定上限（可配，仅超管）

- `system_setting.worker_binding_max_per_boss`：**默认 1**，范围 **1–10 整数**，`is_high_security=1` → **仅超级管理员可改**（普通管理员可读不可写）；
- 读侧每次实时读库（**无缓存**）→ 管理端改完**下一次绑定即生效**；写入非法值 → 400 + 中文（`assertWorkerBindingMax`）；
- 并发安全由唯一键兜底，不只靠服务层计数（见 docs/02 的生成列说明）。

## 补充（2026-10-06）：受限充值管理员会话（`kind=recharge`）+ **管理端双层口径**

负责人定案：老板端「身份」里新增**管理员身份**——最多 **5 个账号**、权限**仅限积分/充值相关**。
它与 companion 是**同一类东西的两个实例**（"受限会话"）：复用同一套机制，不新造一套。
数据模型见 docs/02，接口与错误码见 docs/03，合规红线见 CLAUDE.md 结构规则 12。

### ⚠️ 双层口径（最容易被后人误读的一条，负责人 2026-10-06 明确拍板）

| 入口 | 会话形态 | 权限 | 走哪些接口 |
|---|---|---|---|
| **PC 管理端**（admin-web） | **primary**（正常 `role=admin` 登录） | 窄权限点 `recharge:review` / `recharge:grant` | `/admin/recharge/*` |
| **App 内「管理员身份」** | **受限会话** `kind=recharge`（12h、白名单 ≤5、默认拒绝一切其它接口） | 同样这两个窄权限点 | `/recharge/*` |

**管理端不需要、也不应该套受限会话**：Web 后台本来就是管理员终端，再包一层只会让登录/绑定流程变复杂，
没有额外安全收益。受限会话是为"**手机 App 不应该拿到全权 admin 会话**"设计的。

两条入口**共用同一个服务层**（`RechargeService.reviewList / grant / reject`）——因此幂等、审计、
状态机完全一致，差的只是"用哪种会话进来"。**代码上**：`/recharge/*` 由 `RechargeSessionGuard`
要求 `kind='recharge'`（primary 打了会 403「该接口仅限「管理员身份」受限会话调用…」）；
`/admin/recharge/*` 只按权限点校验，**不要求** `kind`。

### kind 语义（`auth_token.kind` 三值）

| kind | 来源 | 顶号范围 | TTL | 用途 |
|---|---|---|---|---|
| `primary` | `POST /auth/login` 及 `refresh` 轮换 | 只顶该账号其它 **primary**（`revoked=2` + 原文案） | access 2h / refresh 30 天 | 老板态 / 工作端 / 管理端的正常登录 |
| `companion` | `POST /user/identity/bind`（或 `POST /user/identity/refresh` 续期） | **只顶该账号其它 companion**（`revoked=1`），**绝不触碰 primary** | **access 12h 且 refresh 12h**（硬上限） | 老板端内的打手态 |
| `recharge` | `POST /user/identity/bind-recharge-admin`（或 `POST /user/identity/refresh-recharge-admin` 续期） | **只顶该账号其它 recharge**（`revoked=1`），**绝不触碰 primary** | **access 12h 且 refresh 12h**（与 companion 一致） | 老板端内的管理员态（充值审核） |

- 列结构**不需要改迁移**：`auth_token.kind` 是 `varchar(16) DEFAULT 'primary'`（migration `1802000000000` 建的），`'recharge'` 装得下；
  存量行语义逐字节不变（`session-test.js` 13/0 钉死单设备铁律）。
- 会话种类一律**以库中登记为准**，令牌载荷里的 `kind` 只作观测，不参与任何判定。
- 三种 kind 的吊销语句由 `AuthService.issueTokens` 一处产生：`primary` 走原分支（逐字节未改），
  非 primary 走同一条 `WHERE user_id=? AND kind=?` —— 将来再加第四种受限会话也不必改这里。

### 白名单（**默认拒绝**，接口族允许清单）

`common/guards/jwt-auth.guard.ts` 的 `isRechargeAdminAllowedRoute()` 只放行：

1. `/recharge/*` —— 充值审核族：`GET /recharge/requests`、`POST /recharge/requests/:id/grant`、
   `POST /recharge/requests/:id/reject`、`GET /recharge/me`、`GET /recharge/proof/:requestId`；
2. **`/withdraw/*` —— 提现审核族**（**2026-10-11 显式新增**）：`GET /withdraw/requests`、
   `GET /withdraw/requests/:id`、`GET /withdraw/proof/:id?kind=qr|payout`、
   `POST /withdraw/requests/:id/pay-proof`（**打款凭证走专用上传通道**，见下）、
   `POST /withdraw/requests/:id/pay` / `:id/reject`。
   与 `/recharge/*` 同构：Controller 层仍要过 `withdraw:review` / `withdraw:pay` 两个窄权限点，
   且**没有**配置写入接口（改门槛只走管理端 primary 会话）。
   ⚠️ **本条必须显式存在**：受限会话是**允许清单**，不加则整族 403 中文 —— 这正是
   "允许清单而不是黑名单"的设计意图（新接口默认对外关闭）。
   **`pay-proof` 落在同一条前缀内 → 白名单一个字都不用改**；**尤其没有**顺手放开 `/media/*`
   （受限会话直传 `/media/upload` 仍 403 中文）——写侧被收窄到"这一张 `pending` 申请"。
3. `GET /auth/me`（确认"我是谁"）；
4. `POST /auth/logout`（退出管理员态）；
5. `POST /auth/refresh`（12h 窗口内续期）。

其余一律 **403 中文**「受限管理身份仅可处理充值审核，请用管理端完成其它操作」。**特别地**：

- `/admin/*`（**含 `/admin/recharge/*`、`/admin/withdraw/*` 本族自己的管理端接口**）→ 403。理由：那些接口的定义是
  "管理端（`admin:*` 权限）"，受限会话要改配置/收款码必须走管理端登录（primary）——这正是"权限仅限资金审核相关"的落地；
- `/user/*`（`/user/orders`、`/user/wallet`、`/user/identity/*`、`/user/recharge/*`、`PUT /user/profile`…）→ 403；
- `/auth/password`（改密码）→ 403；
- `/media/*` → 403（**刻意不给**：`/media/protected/:id` 对 `role=admin` 放行**任意**受保护媒体，
  受限会话不该拿到这个面；充值凭证改走 `/recharge/proof/:requestId` —— 只放行"这张申请的那张图"，
  详见 docs/待确认事项.md「充值凭证图片的读取通道」）。

与 companion 一样是**允许清单**：**将来新增接口默认对 recharge 关闭**，必须显式加进来才能用。

### 每请求校验（无缓存，每次请求一条 SQL）

校验实现**只有一份**：`modules/auth/recharge-session.check.ts` 的 `checkRechargeSession()`
（与 companion 的 `checkCompanionSession()` 同构）。任一不满足 → **401 中文**：

1. 会话主体仍在 `recharge_admin` **白名单**里（**移出白名单 = 下一次请求立即 401**，文案「受限管理身份已失效，请联系超级管理员重新授权」）；
2. 账号未封禁（`user.status=1`；到期封禁由既有 `AuthService.assertNotBanned` 语义解封）；
3. 账号仍是 `role='admin'`（白名单行在、但角色被改 → 401「该账号已不是管理员…」）。

**权限点是独立一层**：`recharge:review`（读待审列表）/ `recharge:grant`（发放/驳回）由
`PermissionsGuard` 按 `admin_role_permission` 实时校验；两层各管一段，互不代偿。

### 提现：同一套受限会话（2026-10-11）+ **两个新窄权限点**

负责人定案：**打手提现的权限 = 仅超管**，新增两个**窄权限点**（migration `1810000000000`，
**只授予 `super_admin`**，与 `recharge:review` / `recharge:grant` **完全同口径**）：

| code | name | group | 语义 |
|---|---|---|---|
| `withdraw:review` | 提现申请查看 | 提现 | 看列表/详情（**列表与详情都给完整姓名/电话/微信号**：读取者本身即审核人）+ 读收款码与打款凭证 |
| `withdraw:pay` | 提现打款/驳回 | 提现 | **不可逆的资金动作**：打款 = 平台真的把钱转出去了；驳回 = 退回余额 |

- **为什么拆成两个点**：`withdraw:review` 是只读且带敏感个人信息，`withdraw:pay` 是出账动作 ——
  拆开之后"能看不能打"成为一个**可独立授予**的形态（例如财务核对信息、另一人执行打款），
  而不是"要么全给、要么全不给"。两者都**不复用**任何 `admin:*` 大权限。
- **两条入口同一套会话语义**：
  - PC 管理端 = primary（`role=admin`）→ `/admin/withdraw/*`（**不套受限会话**）；
  - App 内「管理员身份」= 受限会话 `kind='recharge'` → `/withdraw/*`（复用**同一个**
    `RechargeSessionGuard`，不新写第二份守卫：受限会话的语义只有一种）。
  两条入口**共用同一个服务层**（`WithdrawService`）→ 幂等、审计、状态机完全一致。
- **受限会话白名单已显式放行 `/withdraw/*`**（见上一节第 2 条）。
- **权限校验是实时的**：`PermissionsGuard` 按 `admin_role_permission` 每次查库 ——
  超管在「角色权限」页取消勾选后，**下一次请求即 403**，不受影响于任何令牌寿命。
- **打款凭证在 App 内也能传（2026-10-11 补）**：受限会话白名单里没有 `/media/*`，
  因此凭证走**专用上传通道** `POST /withdraw/requests/:id/pay-proof`（multipart 字段 `file`；
  `withdraw:pay` + `@Roles('admin')` + `RechargeSessionGuard` 三层闸门照旧）——它**落在已放行的
  `/withdraw/*` 前缀内**，白名单无需新增条目。服务端只认"**这张 `pending` 申请**"：
  已打款 → 中文 400「该申请已打款」；不存在的申请 → 中文 404（不泄漏存在性）；
  老板 / 管理端 primary 打进来 → 403 中文（守卫先于任何存在性查询，没有存在性 oracle）。
  配套地，`pay` 的 `proofMediaId` **必填**（备注可选）：PC 与 App 共用同一处校验，**以更严的为准**。
- **收款信息的完整/脱敏口径（2026-10-11 定案，两条入口一致）**：**列表与详情均给完整**
  （列表行 `account:{realName,phone,wechatId}` + 兼容保留 `accountMasked`）—— 读取者必须持有
  `withdraw:review`（当前只授 `super_admin`），**他本身就是审核人**，隐藏无意义；
  **审计日志与站内通知仍只记脱敏/不含完整手机号**（`operation_log` 是更宽的面：
  能读它的人由「操作日志」权限决定）—— 详见 docs/03「个人信息合规」。**权限点没有新增**。


### 签发 / 吊销

- **签发**：`POST /user/identity/bind-recharge-admin`（`@Roles('user','admin')`，即**持有 primary 会话**才可调，
  与 `/user/identity/bind` 同构）。校验顺序（**刻意把"密码"放在"角色/白名单"之前**：不知道密码的人
  得不到任何"某账号是否被授权"的情报）：
  ① 限流 5 次/分/IP+账号 → 429；② 定位账号 → 400「账号或密码错误」；
  ③ bcrypt（复用 `AuthService.comparePassword`）→ 同一句；④ `role!=='admin'` → 403「该账号不是管理员账号，无法进入管理员态」；
  ⑤ 封禁（复用 `AuthService.assertNotBanned`）→ 403 + `ACCOUNT_BANNED`；
  ⑥ 不在 `recharge_admin` → 403「该账号未获授权进行充值审核，请联系超级管理员」；
  ⑦ `issueRechargeTokens()` 签发受限会话，返回 `rechargeToken` / `rechargeRefreshToken` / `expiresIn=43200` 与 `admin{id,nickname,username}`。
  **签发对象永远是"被验证账密的那个管理员账号"**（主体只来自服务端查库，不取请求体）。
- **续期**：`POST /user/identity/refresh-recharge-admin`（**公开**，**只吃 recharge 的 refreshToken**）。
  kind 闸门与 F5 同一条：非 recharge 令牌（含 primary/companion）**在写操作之前** 401
  「该令牌不是受限管理身份，请重新绑定管理员账号」；续期只顶 recharge、TTL 仍 12h。
- **吊销**：
  - **移出白名单**（`DELETE /admin/recharge/admins/:userId`）→ 删白名单行 + **立即**按
    `user_id + kind='recharge'` 批量吊销该账号全部受限会话（`AuthService.revokeRechargeTokens`）
    + 主动断开其 WS（`RealtimeGateway.disconnectByJti`，防御性，见下）+ 站内通知本人。
    **绝不动 primary** —— 管理员在管理端的登录照常可用（实测：移出后 primary 打 `/auth/me` 与
    `/admin/recharge/requests` 均 200）；
  - 账号被封禁 / 角色被改 → 由**每请求校验**兜住（下一次请求 401），不必依赖写路径挂钩；
  - 同账号再签一条受限会话 → 旧的置 `revoked=1`；登出 / refresh 轮换 → 按既有规则。

### WS（实时网关）

`RealtimeGateway` **在握手阶段直接拒绝** `kind='recharge'` 会话（`assertSessionActive` 抛
`recharge-not-allowed`），**不做心跳校验后放行**。三条理由：

1. 受限会话没有任何实时需求（充值审核是纯 REST 流程）；
2. 它的 `role` 就是 `admin` → 放进来会立刻 `join('admin')` 房间，从而收到**管理端广播**（越权面）；
3. 与白名单同一思路：不需要的能力**默认关闭**，而不是"校验一下再开"。

`removeAdmin()` 仍会调 `disconnectByJti`（正常情况下踢到 0 个）—— 属**防御性**：
若将来有人放开 WS，踢线逻辑已经就位，不必再补一次（这正是安全审计 F1 的教训）。

### 管理员白名单（`recharge_admin`，≤5）

- 权威表 `recharge_admin(user_id PK, granted_by, created_at)`；`user_id` 主键 = 唯一约束。
- **上限 5 由服务端强制**：硬上限常量为 `RECHARGE_ADMIN_LIMIT_MAX = 5`，配置 `admin_limit` 只能在其内**收紧**（1–5）；
  即便配置被写成 10，服务端仍按 5 拒绝 —— 硬上限不依赖配置正确性。
- **仅超管可增删**：`/admin/recharge/*` 的 `POST/DELETE admins` 上先过 `admin:admin:write`（`PermissionsGuard`），
  再过 `assertSuperAdmin()`（角色码 `super_admin` 或 `admin.is_owner=1`，与 `SUPER_ONLY_PERMISSIONS` 的所有者放行同口径）。
  实测：**有** `admin:admin:write` 的非超管 → 403「充值审核管理员白名单仅超级管理员可维护」（证明"仅超管"这条额外闸门真实存在，
  不是被权限点先拦下的假象）。
- **并发安全**（负责人明确要求"唯一约束 + 事务 + 行锁"）：事务内
  ① `SELECT setting_key FROM system_setting WHERE setting_key='recharge_config' FOR UPDATE`
  ——**配置行行锁**把白名单增删串行化（锁 user 行防不住"两个**不同**账号同时加入"这种越限）；
  ② 校验目标账号存在 / `role='admin'` / 档案启用 / 未重复；
  ③ 计数 `< min(admin_limit, 5)` 才插入；④ 撞主键（并发同账号）→ MySQL 1062 翻译成中文 400。
  实测：当前 4 个时**并发加两个 → 恰好 1 个成功**，总数 5，不越限。

## 补充（2026-10-08）：客服权限与「客服大厅」的授权口径

> 配套接口与错误码见 docs/03「补充（2026-10-08）：客服大厅」；实时事件见 docs/07 同名补充。

### 权限来源只有一处：`worker.can_serve_customer`

- **客服权限 = `worker.can_serve_customer = 1` + `worker.status = 1`**，与接单权限 `can_take_order` **完全独立**
  （docs/04 既有口径：一个打手可以只有客服权限、不接单）。授予/撤销仍**只在管理端**
  （`POST /admin/workers/:id/permission`，`type='customer'`）—— 本次**没有**改授予方式、**没有**新增权限点。
- **每请求实时查库、无缓存**：三个新接口（hall / claim / release）都先过 `ChatService.workerOf()`，
  与 `assertWorkerCs` / `sendMessage` 走的是同一个方法、同一张表、同一判据
  （`can_serve_customer=1 AND status=1`）→ 管理端刚撤权限，**下一次请求即 403 中文「无客服权限」**。
- **无客服权限时的返回**：`GET /worker/cs/hall`、`POST …/claim`、`POST …/release` 一律
  **403 中文「无客服权限」**（**不是空列表**）。为什么不学接单大厅的"200 空列表 + `divisionDenied`"：
  接单大厅是**高频首屏**且权限按分部细分（"一个分部权限都没有"是常见状态，报错页会被误读成 App 坏了，
  见 CLAUDE.md 第 10 条）；而**客服入口本就只对持客服权限的账号显示**，"没有客服权限"是**异常状态**，
  按"权限一律中文拒绝"的既有铁律处理更直白。**若负责人希望改成空列表 + 中文提示，是一处 3 行的改动**
  （`csHall` 里把 `workerOf` 换成"查库返回 boolean"）——本条列为待拍板项。

### 会话隔离与"谁看到什么"

| 接口 | 看得到什么 | 判据 |
|---|---|---|
| `GET /worker/cs/hall`（新） | **池子**：所有 `cs`+`open`+**无 active 指派**的会话 | 客服权限（全局，不分会话） |
| `GET /worker/cs/conversations`（既有，语义未改） | **我的**：我被指派的 ∪ 我自己发起的 | 逐会话 active 指派 / 属主 |
| `GET /worker/cs/conversations/:id/{messages,info}`、`POST …/messages`、`POST …/close`（既有，未改） | 只有**当事方**（被指派客服，或该会话属主） | `assertWorkerCs`：先查客服权限，再查该会话 active 指派 |
| `POST /worker/cs/hall/:id/claim`（新） | 池子里的任意一条（这正是"主动接"的定义） | 客服权限 + 会话仍可接入（`cs`+`open`+无 active） |
| `POST /worker/cs/hall/:id/release`（新） | **只动自己那一行 active** | `WHERE conversation_id=? AND worker_user_id=? AND status='active'` 判 affectedRows |

- **接入之后才拿到消息读取权**：`claim` 之前，客服在 `assertWorkerCs` 面前等同"非当事方"，
  `GET …/messages`、`conv:join` 一律 403/404（**大厅只给摘要，不给全文** —— 摘要只有一行、40 字上限，
  且不含任何账号/联系方式）。这是刻意的：**没接单就不该看到完整咨询内容**。
- **存在性口径**：`claim`/`release` 对"不存在"与"不是客服会话"统一回 **404 中文「会话不存在」**
  （安全审计 F3：不让客服借状态码差异枚举平台上还有哪些别的会话）。

### companion（打手态）与受限会话

- **打手态天然可用**：`/worker/*` 是 companion 白名单的**接口族允许前缀**（`isCompanionAllowedRoute`：
  `p === '/worker' || p.startsWith('/worker/')`），因此三个新路由**无需改白名单**、**未改一行守卫代码**；
  打手态在老板端内点「客服大厅」即可直接调用（客户端那批负责 UI）。
  **运行时已实测**（`scripts/tools/cs-hall-e2e.js` ⑧）：`POST /user/identity/bind` 拿 companion 令牌 →
  `GET /worker/cs/hall` **200**、`POST /worker/cs/hall/:id/claim` **200**（打手态真的能主动接）→
  companion 打 `/user/orders` 仍 **403**（受限会话边界未松）→ 解绑后 companion 打 hall **401 中文**。
- **受限会话不受影响**：`kind='recharge'` 的白名单**不含** `/worker/*` → 打 `/worker/cs/hall` 仍是
  **403 中文**（"受限管理身份仅可处理充值审核…"），与本次新增无关（既有行为，未改）。
- **权限验证不依赖连接角色**：`claim`/`release` 的客服身份判定**只看库**（`workerOf(userId)`），
  不看 JWT 里的 role/kind —— primary 打手端与 companion 打手态走的是同一条判定。

## 邮箱绑定/换绑与邮箱验证码登录（2026-10-10）

> 负责人拍板：① **新增「邮箱验证码登录」，密码登录照旧可用（不锁死任何现有账号）**；
> ② **换绑验证 = 当前密码 + 新邮箱验证码**（不是旧邮箱码）。服务端本批全部落地，客户端后续批次。

### 一、`scene` 枚举（**只增不改**）

| scene | 用途 | 发不发信 | 备注 |
|---|---|---|---|
| `register` | 注册（2026-10-05） | 邮箱未被注册才发 | 已被注册 → 400「该邮箱已被注册，请直接登录或使用找回密码」（**逐字未变**） |
| `reset` | 找回密码（2026-10-05） | 已注册才发 | 未注册 → **返回成功但不发信**；**限流判定与额度消耗与已注册侧完全一致**（2026-10-10 账号枚举 oracle 修复第二批，见下） |
| `bind` | 绑定/换绑邮箱（新） | **限流通过就发**，不区分该邮箱是否被别处占用 | 唯一性冲突在 `POST /user/email/bind` 处以 **409** 给出 |
| `login` | 邮箱验证码登录（新） | **仅当该邮箱已绑定某账号才发** | 未绑定 → 响应与真发**逐字相同**、**不发信**，但**限流判定与额度消耗与已绑定侧完全一致**（2026-10-10 账号枚举修复，见下） |

Redis 键含 scene（`email:code:{scene}:{email}` / `email:try:` / `email:last:` / `email:cnt:`），
所以新增两个场景**不会复用或覆盖**注册/找回的码；限流三档（同邮箱 60s / 同邮箱 5 次·小时 / 同 IP 10 次·小时）一字未改。

### 二、防枚举口径（**这是本功能的硬约束**）

- **取码侧（`scene=login` 未绑定、`scene=reset` 未注册 —— 两种"该邮箱在本平台不存在"的情形）**：
  → **HTTP 200 + 与真发完全相同的响应体**（`data.ok=true` + 同一句
  「验证码已发送至邮箱，请注意查收（10 分钟内有效）」），**不发信**（不生成码、不调用 MailerService）；
  内部只落一条 `login_log`（`user_type=user`、`fail_reason='登录取码：邮箱未绑定任何账号（内部记录）'` /
  `'找回密码取码：邮箱未注册（内部记录）'`）供运维排查 —— 该表只有管理端可见，不构成客户端可探测差异。
  - **限流与额度消耗同样对齐（2026-10-10 账号枚举 oracle 修复，两批：`login` 第一批 / `reset` 第二批）**：
    `assertRateLimits()`（只读判定）与 `consumeQuota()`（写 60s 重发锁 + 小时计数）**必须发生在"邮箱是否存在"判断之前**，
    不存在侧照写 `email:last:{scene}:{email}` / `email:cnt:{scene}:{email}`（与存在侧同键同值）。
    **修前的缺陷（两个场景各犯过一次，控制流完全同款）**：不存在分支在限流判定**之前**就 return，既不校验也不扣额度 →
    **同一邮箱 60s 内连发第二次：存在侧 → 429「请求过于频繁，请 N 秒后再试」；不存在侧 → 恒 200**；
    且 Redis 里 `email:last:*` / `email:cnt:*` **只有存在侧存在** —— 两条都是**账号枚举 oracle**
    （`login` 侧可判断"某邮箱是否已绑定本平台账号"，`reset` 侧可判断"某邮箱是否已注册"）。
    首次请求的响应体当时就是逐字相同的，泄漏只发生在**重复请求窗口**与"Redis 里有没有键"两条旁路上。
    `register` 是唯一例外：它**按设计**显式告知"该邮箱已被注册"（400），无需隐藏差异，故其限流仍留在放行路径。
  - **回归与变异**：`scripts/tools/email-auth-e2e.js` ⑦d（`login`）/ ⑦e（`reset`）——
    ① 第二次请求两种邮箱**同为 429 且文案逐字相同**；② 不存在侧**依然 0 发信**（桩 SMTP 真实投递计数 + 存在侧 ≥1 封正向对照）；
    ③ 首次请求仍逐字相同；④ 连发第 3/4 次仍 429；⑤ 不存在侧**同样写 `email:last` / 同样消耗 `email:cnt`**（与存在侧等值）。
    变异验证 **M3**（`login`：把限流/额度挪回"是否已绑定"判断之后）/ **M4**（`reset`：挪回"是否已注册"判断之后）
    必须变红（实测各红 6 条）。代码侧的顺序不变量写在 `AuthService.sendEmailCode` 的 `login` / `reset` 分支前
    （含"为什么限流必须先于存在性判断"、"禁止挪回"与"register 是唯一例外"）——**禁止调换**。
  - ⚠️ **残余差异（无法消除，如实记录）**：存在侧那次要真发一封 SMTP（生产数百毫秒），不存在侧不发信，
    因此**耗时**维度上仍可分（响应体、状态码、限流、Redis 键已全部对齐）。这是"不存在侧绝不发信"的必然代价，
    `login` 与 `reset` 同一取舍；要做掉它只能给不存在侧补一段等长的假延迟（本轮未做，需负责人定案）。
- **登录侧**（`POST /auth/login` 带 `email`）：「邮箱没绑账号」「码不对」「码过期」「错满 5 次作废」
  四种情况**同一句话同一个状态码**：**400 邮箱或验证码错误**。
  为此**验码成功之前不做角色校验与封禁校验** —— 否则 `role` 传错时的 403「账号角色不符」、
  封禁账号的 403「已被封禁」本身就变成"该邮箱已绑定账号"的判别式（登录日志里仍记真实原因）。
- **`bind` 场景刻意不防枚举**：绑定侧要给出 409，若取码阶段静默不发，用户永远拿不到码 → 409 这条路径
  在真实使用中不可达；而"邮箱是否已注册"这条信息本来就能从 `scene=register` 拿到（既有口径），
  静默不发换不来任何额外收益。**若负责人要收紧 register 场景的枚举口子**，需单独定案（会改既有行为）。

### 三、单设备铁律的关系（**一点没松**）

邮箱验证码登录就是**一次 primary 登录**，与密码登录走**同一个** `AuthService.issueTokens(user)`：

- **primary ↔ primary 仍互斥**：邮箱码登录成功时，该账号此前的 primary 会话被置 `revoked=2`，
  旧 access 下一次请求 **401「账号已在其他设备登录」**（e2e 有实测断言）；
- 会话语义、TTL（access 2h / refresh 30d）、`login_log` 口径、返回体结构**全部与密码登录一致**；
- **不触碰 companion / recharge**：打手态与受限管理态不受任何影响（`kind='primary'` 过滤，既有实现）；
- 工作端到期收口同样生效：`role=worker` 的邮箱码登录 → 403「工作端已停止服务…」（判定与文案复用
  `modules/auth/worker-app-sunset.ts`，未新增第二份判定）。

### 四、角色范围（**两处都需要负责人过目**）

| 能力 | 放行角色 | 理由 |
|---|---|---|
| `POST /user/email/bind`、`GET /user/email` | **`user` + `worker`**（primary） | 老板与打手都是平台账号，打手同样需要邮箱找回/登录能力；到期收口后 worker primary 本身就会被 401 挡掉，放行不产生额外能力 |
| `POST /auth/qq/bind` | **仅 `user`** | 账号级第三方绑定按"老板侧能力"收口（与 `POST /user/identity/bind` 同口径） |
| `POST /auth/qq/login` | 命中的账号必须是 **`role=user`** | 否则 403「该 QQ 未绑定老板账号」—— 防止 QQ 登录凭空造出 worker primary 会话绕过工作端到期收口 |
| **`admin` 一律不放行上图任何一条** | — | 管理端账号由后台创建、走 PC 后台登录。**把绑邮箱入口对 admin 收窄，admin 就永远拿不到"邮箱码登录"这条路**（账号必须先有已验证邮箱才可能走邮箱码登录）；`POST /auth/login` 本身不做角色特殊分支（少一处分叉），靠"入口收窄"实现同样的效果 |

**companion（打手态）与 recharge（受限管理态）一律 403**：`jwt-auth.guard.ts` 的
`isCompanionAllowedRoute` 是**允许清单**，`/user/email/*` **不在其中且不得加入** ——
companion 是老板手上 12h 的受限会话，若它能改打手账号的邮箱，
老板就能"绑自己的邮箱 → 用找回密码改掉打手密码 → 永久占有打手账号"（明确越权面）。
e2e 有纯函数断言把这个边界钉死。

### 五、审计留痕（与邮箱注册/找回**同口径**）

## QQ 登录（服务端，2026-10-10）

> 客户端与 **QQ APP ID/Key 尚未拿到** → 本批只做服务端：先把接口、复核链路、建号/绑定策略与
> "未配置时的行为"全部落地并用本地打桩验证；拿到 APP ID/Key 后只需在 `server/.env` 填两行即可上线。
> **不引入腾讯 SDK**（Node 内置 `fetch` + `AbortSignal.timeout(10s)`）。

### 一、表结构 `user_oauth`（migration `1809000000000`，已执行）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | bigint unsigned PK | 自增 |
| `provider` | varchar(16) | `qq`（当前）/ `wechat`（预留，表结构与服务层都按多 provider 写） |
| `openid` | varchar(64) | 第三方平台用户标识（QQ 为 32 位十六进制）——**只信服务端复核结果** |
| `unionid` | varchar(64) NULL | 跨应用统一 id（`oauth2.0/me?unionid=1` 才有）；**只存不判**，备将来合并 |
| `user_id` | bigint unsigned | 平台账号（`user.id`），索引 `IDX_user_oauth_user_id` |
| `created_at` / `updated_at` | datetime(3) | 审计时间 |

- **唯一键 `UK_user_oauth_provider_openid(provider, openid)`** = "一个 QQ 只能绑一个平台账号"的**数据库级**权威约束
  （并发下服务层"先查后插"必被绕过；撞键回中文 409，不是 500）；
- 反方向是 N:1：**一个平台账号可绑多个 QQ**（登录时任一个都能进同一账号），两者不冲突。

### 二、复核流程（**绝不相信客户端传的 openid**）

```
POST /auth/qq/login  { accessToken, openid? }
  0) QQ_APP_ID / QQ_APP_KEY 任一为空 → 中文 503「QQ 登录未配置」，**不做任何网络调用**（打桩实测 0 命中）
  1) GET https://graph.qq.com/oauth2.0/me?access_token=…&fmt=json&unionid=1   （10s 硬超时）
     → 权威 openid / unionid；返回体里的 client_id 必须 == QQ_APP_ID（别家应用的 token → 400）
     → 兼容腾讯的两种返回形态：JSON 本体 与 `callback( {...} );` 包裹（两种都有 e2e 断言）
  2) 入参 openid 与服务端结果**比对**：不一致 → 403「QQ 授权校验失败：openid 与服务端复核结果不一致」
     （不建号、不登录、不绑定；伪造/串号在这里被挡住 —— 变异验证 M2 的靶子）
  3) 查 user_oauth(provider='qq', openid=服务端结果)
     ① 命中 → 直接登录该账号（角色/封禁/单设备顶号全部沿用既有登录实现）
     ② 未命中 → GET user/get_user_info（取昵称；**失败只降级为无昵称**，不影响登录）→ 建新老板账号 + 写 user_oauth
```

**超时与失败**：两次网络调用各自 10s 硬超时（`AbortSignal.timeout`），
超时/网络失败 → 503「QQ 登录服务暂时不可用，请稍后重试」；凭证类失败 → 400「QQ 授权已失效，请重新授权后登录」。
**`access_token`/`QQ_APP_KEY` 绝不进日志**（日志只记原因与 `client_id`）。

### 三、绑定策略

| 情况 | 行为 |
|---|---|
| `(qq, openid)` 已存在 | **直接登录该账号**（不新建、不重复绑；`isNewUser=false`） |
| `(qq, openid)` 不存在 | **建新账号**（`role=user`）+ 同事务写 `user_oauth` + 建钱包；响应 `isNewUser=true` |
| 请求带已登录身份（`POST /auth/qq/bind`，`@Roles('user')`） | 复核通过 → 绑到当前账号；该 QQ 已绑到**别人** → 409「该 QQ 已被其他账号绑定」；已绑到**自己** → 幂等成功（`alreadyBound=true`） |
| 并发首次登录 | `UK_user_oauth_provider_openid` 撞键 → 事务整体回滚（**不留孤儿账号**）→ 复查绑定行 → 复用刚建好的账号登录 |

**新账号的字段口径（"沿用注册的既有实现"，不自己发明）**：

- `uid`（展示 ID）→ **`AuthService.generateUid()`**：`U` + 10 位随机数字 + 唯一性重试（与注册**逐字同一实现**）；
- `username` → 注册时由用户输入，QQ 登录没有输入，因此按 openid 派生 `qq_<openid 字母数字部分>`（截断 28 位），
  占用则追加 4 位随机数字重试（与 `generateUid()` 同一种"生成 + 查重重试"写法）；
- `nickname` → QQ 昵称（去控制字符 + 按**字符**截断 32，避免 emoji 被截成半个代理对）；
  取不到 → `QQ用户<openid 后 4 位>`；
- `password_hash = ''` → **第三方账号没有密码**（`password_hash` 列 NOT NULL，故空串而非 NULL）；
  既有登录逻辑对空 hash 一律按"账号或密码错误"处理（e2e 有断言）；
  用户可后续用「邮箱验证码重置密码」给自己设一个密码，从而获得密码登录能力；
- **头像不落库**：本站头像是 media 体系（`user.avatar_media_id`），没有"外链头像"列；
  `figureurl_qq_*` 只随 `fetchUserInfo` 返回值带出，不入库（将来要存需先把图片转存为 media）。

### 四、未配置时的行为（**拿到 APP ID/Key 前的默认态**）

- `POST /auth/qq/login` 与 `POST /auth/qq/bind` 一律 **503 + 中文「QQ 登录未配置」**；
- **零网络调用**（e2e 用本地打桩服务器断言命中数 = 0）→ 没配置时服务端可以先上线，不会因外呼抖动/超时影响任何请求；
- 配置项写在 `server/.env.example`（`QQ_APP_ID` / `QQ_APP_KEY` / `QQ_GRAPH_BASE_URL`），**只占位、不含真实值**；
  `QQ_GRAPH_BASE_URL` 默认腾讯线上地址，**仅供本地打桩/联调测试**（生产保持留空）。

### 三、越权自测（已覆盖的判定）

1. 用**别人**的 `orderId` 调 `POST /user/orders/:id/review` → 404「订单不存在或不属于你」（不区分不存在/不属于）；
2. `worker_user_id`（打手态 companion 令牌）调 `/user/orders/:id/review` → **403 中文**（白名单默认拒绝）；
3. 普通管理员（非超管、无 `review:moderate`）调 `/admin/reviews*` → **403「无权限」**；超管 → 200；
4. 公开接口不带任何令牌 → 200，且响应里**不含** `uid`/手机号/`user.id`/真实昵称（只有 `nicknameMasked`）；
5. `hidden=1` 的评价在 `/public/workers/:id` 与 `/public/workers/:id/reviews` **一律不出现**，
   且不再计入 `reviewCount` / `satisfiedRate`。
