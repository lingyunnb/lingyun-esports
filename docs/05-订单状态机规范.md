# 05 - 订单状态机规范

## 状态码

| 状态码 | 中文 | 说明 |
|---|---|---|
| pending_take | 待接单 | 在大厅等待抢单或派单 |
| pending_dispatch | 待确认派单 | 已派给指定工作端，等待确认（对大厅不可见） |
| taken | 已接单 | 工作端已接单，服务开始前 |
| in_progress | 进行中 | 工作端已开始服务 |
| pending_confirm | 待用户确认 | 工作端提交完成，等待用户确认 |
| completed | 已完成 | 用户确认完成（或确认超时自动完成，规则待 M5 确认） |
| canceled | 已取消 | 含退款处理（见 docs/06） |
| abnormal | 异常 | 服务异常，由管理员介入 |
| after_sale | 售后/申诉 | 用户发起申诉，管理员裁决 |

## 合法迁移表（唯一依据；非法迁移返回 400 并写安全审计）

| 原状态 | 允许迁移到 |
|---|---|
| pending_take | taken（抢单成功）、pending_dispatch（派单）、canceled（用户取消/管理员取消） |
| pending_dispatch | taken（工作端确认）、pending_take（拒绝/超时/管理员撤回）、canceled |
| taken | in_progress（工作端开始）、canceled（工作端取消/管理员取消） |
| in_progress | pending_confirm（工作端提交完成）、abnormal、canceled |
| pending_confirm | completed（用户确认）、after_sale（用户申诉）、abnormal |
| completed | after_sale（申诉窗口期内，窗口由 system_setting 配置） |
| after_sale | completed、canceled（含退款）、abnormal（管理员裁决） |
| abnormal | after_sale、canceled、completed（管理员裁决） |

## 状态变更规则

1. 客户端**不能直接修改订单状态**；所有变更走服务端状态机服务，先校验迁移表再执行
2. 每次状态变化**必须**写 order_status_log：原状态、新状态、operator_type(system/user/worker/admin)、operator_id、source(client/ws/cron/admin)、request_id、备注
3. 抢单/派单确认/拒绝/超时回退统一用**条件 UPDATE 判 affectedRows**（`WHERE id=? AND status=期望原状态`），并发时只有一个成功；禁止 Redis 锁与数据库双源
4. 状态机服务与业务动作（扣款/退款/统计累加）在同一事务内

## 各状态下的操作者权限

| 操作 | 执行者 | 前置状态 |
|---|---|---|
| 下单 | user | 创建即 pending_take |
| 取消 | user（仅 pending_take 前）/ worker（taken、in_progress 且未实质开始）/ admin（任意未终态） | 见迁移表 |
| 抢单 | worker（can_take_order=1 实时校验，且进行中订单数未达上限） | pending_take |
| 派单 | admin（admin:order:dispatch） | pending_take |
| 确认/拒绝派单 | 被派单的 worker 本人 | pending_dispatch |
| 开始服务 | 接单 worker 本人 | taken |
| 提交完成 | 接单 worker 本人 | in_progress |
| 确认完成 | 下单 user 本人 | pending_confirm |
| 申诉 | 下单 user 本人 | pending_confirm / completed（窗口期内） |
| 裁决/标记异常 | admin | after_sale / in_progress 等 |

## 超时规则（默认值，M5 前向负责人确认，全部 system_setting 可配）

| 超时 | 默认 | 处理 |
|---|---|---|
| 派单确认 | 5 分钟 | cron 每分钟扫描 dispatch_expire_at 过期 → 条件更新回 pending_take，source=cron |
| 用户确认 | 暂不自动完成（待确认） | 由管理员介入 |

## 派单流程细节

1. 管理员派单：校验目标 worker 在职且有接单权 → 条件更新置 pending_dispatch（记录 dispatch_worker_id/dispatch_admin_id/dispatch_expire_at）→ 写状态日志 → WS 通知目标 worker（dispatch:new，含订单摘要与倒计时）
2. worker 确认 → taken；拒绝 → 回 pending_take（同单不自动再派给同一人，记录状态日志备注）
3. 超时 → cron 回 pending_take；到期前 1 分钟 WS 提醒
4. 派单期间订单对大厅不可见（大厅只查 pending_take）

## 异常与售后

- abnormal：工作端报告异常或管理员标记；管理员裁决后迁移到 after_sale / canceled / completed
- after_sale：用户申诉（order_appeal 表）；管理员裁决：驳回（回 completed）、支持（canceled + 全额/部分退款，退款走积分流水 order_refund）
- 退款必须事务内：条件增余额 + 写流水（同订单同 change_type 只记一次，应用层校验）
- **退款时战绩与钱包必须同步回退**（2026-10-06 定案，**不可只做一半**）：已结算订单退款先按 `order_settlement` 落库金额冲正打手与平台
  （`settlement-reversal` / `platform_commission_reversal`）+ 全额退老板（`order_refund`），
  **并在同一事务内**把该单结算时累加的 `worker_stats` 一起退回（`-1 单 / -1 完成 / - 原结算额`）。
  只退钱不退战绩 = 走完全合法的售后退款链之后**打手战绩与榜单永久虚高**（2026-10-06 实测：
  打手 167 显示 4单/4完成/352.00，实际有效完成 0）。判定口径、幂等与"不许负值"的做法见 docs/06 第 7 条。

## 订单完成结算（抽成比例**后台可配**，默认平台 25% / 打手 75%）

- **比例来源（唯一真相）**：`system_setting.platform_commission_rate`，`cfg_value = {"value": 25}`，语义 = **百分数整数**（25 = 平台抽 25%、打手拿 75%），取值范围 **0–50 的整数**，非法值后端 400 拒绝（中文）；管理端「系统设置」页可视化修改（权限 `admin:setting:read/write`）。详见 docs/06 同名补充章节
- **触发**：①老板端"确认完成"（pending_confirm → completed）②管理端强制完成（pending_confirm/abnormal/after_sale → completed）—— 两条路径共用同一个收口 `OrderService.completeOrderTx`；已结算订单只补状态、**绝不二次结算**
- **金额**：以订单创建时的 total_amount 快照为准（绝不使用商品当前价格）；服务器计算
  `workerAmount = round(total × 打手比例) / 100`（四舍五入到 0.01，**修正本文档早期写的 floor**——代码一直是 round）、
  `platformAmount = total - workerAmount`（保证 `worker + platform === total` 严格守恒）；客户端不可传金额/比例
- **入账**：打手按分成比例入工作端账号自己的钱包（change_type `order_settlement`，reason 带生效百分比）；平台按抽成比例入平台账户钱包（uid PLATFORM1，change_type `platform_commission`）；双方流水含前后余额快照与订单关联
- **比例落库留痕**：`order_settlement.worker_percentage / platform_percentage` 记录**结算当时**的生效比例，管理端订单详情按该值展示；已结算订单退款按该记录金额冲正，改比例不影响历史单据
- **幂等（一个订单最多结算一次，三重保证）**：①订单行锁串行化 ②状态机检查（非允许状态拒绝）③order_settlement.order_id 数据库唯一约束
- **原子性**：确认完成 + 打手入账 + 平台入账 + 结算记录 + 状态流转 + 状态日志 + 销量累加在同一事务，任一步失败整体回滚，无半结算状态
- **取消/异常/售后**：已取消、异常、售后订单一律不能结算；取消（待接单阶段）全额退款（order_refund）
- **审计**：order_settlement 唯一记录（结算号/金额/比例/时间/请求ID）+ order_status_log 全流转留痕；抽成中心（admin/commission/stats、admin/settlements）SQL 实时统计，不写死
- **验收实测（39 项）**：连续点击/5 并发确认仅 1 次结算；两 worker 并发抢单仅 1 人成功；越权 404、无权限 403、篡改字段 400；结算守恒 Σ订单额 == Σ打手+Σ平台

## 补充（2026-10-04）：退款申请（顶部导航「退款」）与状态机的关系

老板端顶部导航新增「退款」入口：对**未结束订单**（未开始 / 进行中 / 待确认）提交退款申请 → 管理端审批。

| 项 | 规则 |
|---|---|
| 可申请状态 | `pending_take` / `pending_dispatch` / `taken` / `in_progress` / `pending_confirm`（`system_setting.refund_apply_statuses` 可配） |
| 已完成订单 | **不走退款申请**，走既有售后申诉（`completed → after_sale`） |
| 审批通过 | 订单 → `canceled`（与 `cancelByAdmin` 同路径：管理员可取消任意未终态订单，故 `pending_confirm → canceled` 是既有行为，不是新增迁移）；同事务全额退回老板积分（未结算退订单金额，已结算先冲正 70/30） |
| 审批驳回 | 订单状态**不变**（回到申请前状态），必须填理由 |
| 留痕 | 通过/驳回都写 `order_status_log`（operator_type=admin，source=admin）；审批走 `UPDATE ... WHERE status='pending'` 条件更新，重复审批 400，绝不二次退款 |
| 会话收尾 | 与其它取消路径同一规则（`settleCanceledDirectChatTx`，方案①） |

> 说明：`pending_confirm` 在合法迁移表里只能到 `completed`/`abnormal`，但**管理员取消**（docs/05「各状态下的操作者权限」：admin 可取消任意未终态）本就允许该迁移，退款审批复用同一实现，未新增状态机边。
