# 30 · 打手态「通知栏提醒」（新单 / 消息）

> 负责人 2026-10-15 原话：「**在打手端加一个功能：当用户在打手端时有单子和客服要发提醒到通知栏，
> 就像微信来消息了那样**」
>
> 本文是这条需求的**落地口径 + 边界说明书**。所有"做到哪一步""没做到哪一步"都写在正文，
> 不要凭印象向负责人承诺"和微信一样"。

---

## 1. 一句话结论（先看这个）

**打手态下，新单进大厅、客服/老板发消息 → 系统通知（横幅 + 声音 + 震动），点通知落到对应页面；
只在本 App 进程存活期间有效（划掉 App 就收不到）。**

## 2. ⚠️ 真实边界：没有推送服务，通知只能"进程活着"时才到

本仓库**没有接任何推送服务**（无 FCM、无厂商推送通道，`pubspec.yaml` 里没有 firebase_messaging，
后端也没有推送模块）。通知的事件来源是 `RealtimeClient`（Socket.IO，`/ws/chat`）——
**WebSocket 只在 App 进程存活期间在线**：

| 场景 | 能不能收到通知 | 原因 |
|---|---|---|
| App 在前台（在任意一屏，包括老板态以外的打手态页） | ✅ 能 | 进程活着、WS 连着 |
| 刚切到后台（最近任务里还看得见） | ✅ 能（多数机型几十秒～几分钟） | 进程还活着、WS 还连着；系统回收后就不能 |
| 用户**从最近任务划掉 App** | ❌ 不能 | 进程被杀 → WS 断开 |
| 系统内存回收 / 后台被冻结（Doze、国产 ROM 清理） | ❌ 不能 | 同上 |
| 断网 / 隧道不通 | ❌ 不能 | WS 连不上（会走地址看门狗自愈，但断开期间的事件收不到） |

**这不是实现缺陷，是没有推送服务时的物理上限。** 要真正做到"关掉 App 也能收到"，
只有两条路（都需要负责人决策、都不在本轮范围内）：

1. **接推送服务**：FCM（国内需自建通道或 GCM 不通）或厂商推送（小米/华为/OPPO/vivo）。
   需要：各家开发者账号 + 后端新增推送模块 + 客户端新增 SDK 与 `google-services.json`
   之类配置 —— 这是"像微信"的**完整形态**，也是**唯一可靠**的形态。
2. **前台服务保活**（见 §7）：能显著改善"刚切后台"，**救不了**"划掉 App"，
   且要付常驻通知的产品代价。

## 3. 两个通知渠道（Android 8+，用户在系统设置里能单独关）

渠道 id / 名称 / 描述的唯一出处是 **`apps/packages/core/lib/src/notify/worker_notice.dart`
的 `WorkerNoticeChannel`**（`boss-app` 侧不再写第二份字符串）。

| 用途 | channelId | 渠道名（用户可见） | 描述（用户可见） | importance | 声音 | 震动 |
|---|---|---|---|---|---|---|
| 新订单 | `worker_orders` | 新订单 | 有新单进接单大厅时提醒你 | `Importance.high` | ✅ | ✅ |
| 消息 | `worker_messages` | 消息 | 客服或老板发来消息时提醒你 | `Importance.high` | ✅ | ✅ |

- **为什么要分两个渠道**：微信也是这么做的 —— 新单和消息是两种完全不同的打扰，
  用户可能只想要新单、不想被消息刷屏（或反之）。合一个渠道就**做不到**这件事。
- `Importance.high` + `Priority.high` = **横幅（heads-up）**，不是"只在抽屉里躺着"。
  `Priority` 是给 Android 8 以前用的，两个都给。
- ⚠️ **渠道参数一旦创建就被系统锁死**（Android 规定）：以后改 importance/声音**不会**对老用户生效，
  只能换新 channelId 或让用户自己去系统设置里改。
- 不声明 `RECEIVE_BOOT_COMPLETED` / `SCHEDULE_EXACT_ALARM`：本功能**不用定时通知**
  （通知全部来自前台实时通道），用不到就不要权限。

## 4. 触发与抑制（"像微信却不烦人"的关键）

判定全部收敛在 **`WorkerNoticeGate`**（纯函数，单独可测），**唯一出口**，不许在别处再写一遍。

| 事件 | 发通知的条件 | 明确**不**发的情形 |
|---|---|---|
| `order:new`（新单） | ① 当前在打手态 ② **不在**接单大厅那一屏 ③ 回源后该单**确实在我的接单大厅里** ④ 正文至少能说出一句真话 | 老板态/管理员态；正在看大厅；无权限分部/已被抢/已取消（回源列表里找不到）；`status=taken/canceled` 的复用广播 |
| `msg:new`（消息） | ① 当前在打手态 ② `senderType == 'user'`（**对方**发的） ③ **没在**看这条会话 ④ 这条会话在【客服/老板】两段里 | 老板态/管理员态；自己发的（`worker`，房间会把我的消息推回来）；系统消息（`system`）；正在看该会话；好友会话 / 已结束的客服会话（**不知道发送方是谁就别乱弹**） |

- **"在那一屏"的判定数据源**是 `WorkerNotifyPresence`：
  - `hallVisible` —— 由**打手态壳**写（底栏停在第 1 项时）。为什么必须壳写：
    打手态用 `IndexedStack`，三页**同时挂载**，"页面 mounted"根本区分不出当前看的是哪一屏；
  - `openConversationId` —— 由**宿主 App**写（`home_shell.openWorkerChat` 压上聊天页期间），
    core 拿不到宿主 push 的聊天页。
- **`order:new` 这个事件名被服务端复用**：新单是 `{orderId}`，而"被抢/取消"也广播 `order:new`
  但带 `status`。只有新单才弹「有新订单」——对"被抢/取消"弹"有新订单"就是**撒谎**。

### 4.1 文案（不得编造）

正文**只用服务端真的给了的字段**，拿不到的那一段**整段不写**（不占位、不猜、不显示 UUID）：

- 新单：`<分部名> · <商品名> ¥<金额>` 换行 `单号 <orderNo>`
  （分部名来自 `/worker/division-permissions` 的 `label`；商品名/金额/单号来自 `/worker/order-hall`）
  —— 全空则**不发**（"一条真话都说不出来就不发"）。
- 消息：标题 = 客服会话固定「祁连山客服」/ 老板直聊用**老板昵称**（缺失才退回「老板」）；
  正文 = 一行摘要（与消息页同口径：撤回 → `[消息已撤回]`、图片 → `[图片]`、非文字 → `[新消息]`、
  超 60 字截断）。
- 金额一律走 core 的 `fmtMoney`（`¥38.00`），**不自己拼**。

## 5. 点击跳转（含冷启动）

- 通知 payload = `{"v":1,"k":"order|message","c":"<会话id>"}`（`WorkerNoticeRoute.encode`）。
- **App 存活时**点通知：`onDidReceiveNotificationResponse` → 解析 → `WorkerNotifyHub.requestRoute`
  → 打手态壳**立即**切到对应 tab。
- **App 被杀后点通知冷启动**：`getNotificationAppLaunchDetails()` → 同样的 `requestRoute`
  → 壳**一挂载就消费**（`_consumeNoticeRoute` 在 `initState` + `ValueNotifier` 监听里各做一次）。
- 落点：**新单 → 接单大厅**（底栏第 1 项）；**消息 → 消息页**（底栏第 2 项，本版**不**直接钻进那条会话）。
- 待处理请求有 **2 分钟保鲜期**（`WorkerNoticeRoute.ttl`）：点完通知过了五分钟才进打手态，
  这时再抢用户的视线去跳转是打扰 —— 过期请求**直接作废**（无论是否过期都会被取走，不残留）。
- 坏 payload（null / 截断 JSON / 未知 `k`）→ `decode` 返回 null → **只打开 App，不跳**，绝不崩。

## 6. 运行时权限与降级

- Android 13+ 的 `POST_NOTIFICATIONS`：**进打手态时问一次**，顺序刻意是
  「先查已授权 → 再查有没有问过 → 才弹窗」：
  1. 已开着（含 Android < 13）→ 什么都不做（**绝不弹空窗**）；
  2. 之前问过（含被拒）→ **不再反复弹**（标记落 `AppSettings`，跨启动也记得）；
  3. 第一次且没开着 → 弹一次；被拒 → 给**一条**中文说明
     （「未开启通知权限：新单和消息不会提醒，可在系统设置里打开」），之后**静默降级**。
- 全链路不抛：查权限/请求权限/发通知任何一步失败都**不影响接单**（通知是增强功能，不是业务链路）。
- 用户后来在系统设置里自己打开 → 下一次 `notificationsAllowed()` 读到 true，功能自动恢复。

## 7. 下一步选项（负责人决策）：前台服务保活

**默认不做**。若负责人认为"切后台几分钟就必须能收到"是硬需求，可选方案与代价：

| 项 | 内容 |
|---|---|
| 做法 | 打手态期间起一个**前台服务**（`FOREGROUND_SERVICE` + 常驻通知 + `foregroundServiceType`），服务里维持 WS/心跳；`flutter_local_notifications` 自带 `ForegroundService`，也可自写 |
| 需要的声明 | `FOREGROUND_SERVICE`；Android 14+ **必须**声明具体类型，长连接场景只能用 `dataSync` → 还要 `FOREGROUND_SERVICE_DATA_SYNC` 权限，并在 manifest 的 `<service>` 上写 `android:foregroundServiceType="dataSync"` |
| 产品代价 | **通知栏常驻一条"祁连山电竞 正在运行"**（用户可长按屏蔽 → 功能失效）；耗电与内存占用上升；国产 ROM 仍可能清；**用户划掉 App 依旧收不到** |
| 平台限制 | Android 15 起 `dataSync` 前台服务**每天有累计时长上限**（超时被停）→ 长时间保活不可靠；`mediaPlayback`/`location` 等类型与本场景不符，别硬蹭（会被商店审核拒） |
| 结论 | 它只把天花板从"刚切后台"抬到"后台更久一点"，**换不来"微信级"**；真要做完整形态应走 §2 的推送服务路线。**由负责人决定，本轮不做。** |

## 8. 分层与文件清单（谁负责什么）

| 层 | 文件 | 职责 |
|---|---|---|
| core（纯逻辑，无平台依赖） | `apps/packages/core/lib/src/notify/worker_notice.dart` | 渠道常量 / 通知与落点模型 / **事件 payload 解析** / **判定门** / 文案拼装 / 通知 id 分配 |
| core | `apps/packages/core/lib/src/notify/worker_notify.dart` | `WorkerNotifier` 接口（平台能力）、`WorkerNotifyPresence`（在场状态）、`WorkerNotifyHub`（注入 + 待处理跳转）、`WorkerNotifyService`（订阅→判定→回源→发） |
| core | `apps/packages/core/lib/src/identity/worker_shell.dart` | 接线点：进打手态启动派发 / 退订 / 写在场状态 / 消费跳转请求 / 请求一次权限 |
| boss-app（平台实现） | `apps/boss-app/lib/services/worker_local_notifier.dart` | `flutter_local_notifications` 实现：建两个渠道 / 权限查询与请求 / show / 点击回调 / 冷启动读启动详情 |
| boss-app | `lib/main.dart` | 注入实现（`WorkerNotifyHub.instance.notifier = WorkerLocalNotifier.instance`）+ 冷启动跳转补登记（**不 await**，不挡首帧） |
| boss-app | `lib/pages/home_shell.dart` | `openWorkerChat` 期间写 `openConversationId`（压着聊天页时抑制该会话通知） |
| boss-app | `android/app/src/main/AndroidManifest.xml` | `POST_NOTIFICATIONS` + `VIBRATE` |
| boss-app | `android/app/build.gradle.kts` | `isCoreLibraryDesugaringEnabled = true` + `desugar_jdk_libs:2.1.4`（插件硬要求，见 §9） |

**为什么平台实现不放进 core**：core 同时被**已冻结的工作端**（`apps/worker-app`）复用，
往 core 引平台插件会连带改冻结端的依赖树；且 core 单测可以在**不碰系统 API** 的前提下
用假通知器把判定逐条钉死（与 `WithdrawMedia` 把选图能力留给宿主注入是同一条路线）。

## 9. 已知风险

- **desugaring**：`flutter_local_notifications` 10+ 硬要求开 `coreLibraryDesugaring`（即使不用定时通知）。
  该插件 README 记录过"开 desugaring 后 Android 12L+ 极少数设备崩溃"的**历史**报告
  （Flutter issue #110658），官方给的兜底是补 `androidx.window` 依赖。
  本机 `flutter build apk --debug` 通过；**真机 12L 若出现启动崩溃**，按 README 补
  `implementation("androidx.window:window:1.0.0")` 两行即可 —— 属于**未验证项**，不预先加（避免无意义依赖）。
- 通知小图标用 `@mipmap/ic_launcher`（启动图标）。官方建议用 drawable 单色图标（否则状态栏里
  可能显示成一个白块）。本轮不新增图标资源（要设计稿审批），列为可优化项。

## 11. 需服务端配合项

**0 项。** 本轮全在客户端：只用既有事件（`order:new` / `msg:new`）与**已在伴随会话白名单内**的
读接口（`/worker/order-hall`、`/worker/division-permissions`、`/worker/cs/conversations`），
`server/**`、`admin-web/**` 一行未动。将来若要"关掉 App 也能收到"，才需要服务端接推送（§2）。
