合规形态已定案：线下收款 + 人工审核。收款码是管理端上传的图片，老板扫码在平台外付款 → 上传转账截图 → 提交申请 → 管理员核对后手工加积分。 全链路不接任何支付通道，提交后唯一文案是「申请已提交，等待审核」，不做提现。金额 6 / 10 / 20 / 38 / 68 / 98 / 128 / 198 / 328 / 648 元 + 自定义（1–10000），1 元 = 10 积分，每人待审核上限 3 笔。

先看结论（详见第 8 节）
  • 入口推荐 A 套（三宫格扩四宫格）：唯一同时满足「同一入口只出现一次零风险 + 首屏成本 0dp + 改动最小」的方案。实测：入口 36dp 高、落在第 4 格（右起 285–373dp），「选择分部」首卡位移 0dp，底部小字与官方馆 Y 坐标一动不动（787 / 668），首屏余量仍为 57dp。代价是这一行的语义要从"售后三件套"扩为"自助服务"，有解。
  • 备选 C 套（独立通栏条）：与已落地的 RechargeCopy.entryTitle + entrySubtitle 逐字同构，客户端实施成本最低；但要先裁两件事 —— 通栏条与宣传图通栏谁先（有宣传图时会切断"通栏紧贴导航"的既有定案）、条上要不要带余额数字（带 = 同一个余额在两处显示）。实测首屏代价：+54dp，首屏余量 57dp → 3dp。
  • 不推荐 B（顶部导航右侧）：把资金动作塞进"内容入口行"，与 2026-10-04「投诉/打赏/退款 单独成行、不与内容入口混装」的既有判断正好相反；且 1.3× 系统字号下该行已占 279 / 358dp。
  • 不推荐 D（欢迎语行积分胶囊）：会抢掉首页唯一的实时数据「N 位在线」，还要么把负责人指定原文挤到 3 行、要么删掉在线数；更关键的是「积分 1,286 ›」点进去是充值而非积分明细 → 心智错配。
  • 充值页推荐形态 1（档位网格 + 底部收款码卡），与 A/D 天然搭配；审核压力大时备选形态 3 两步式。
  • 未配置收款码 → 入口整块不渲染（与已落地的 RechargeConfig.entryAvailable 同源），理由见第 7 节。

7「未配置收款码」的处理结论

结论：入口整块不渲染（连高度都不占），并保留深链兜底
  • 与已落地代码同源：core 的 RechargeConfig.entryAvailable = hasQrCode && (有档位 ∨ 可自定义) && 比例 > 0 —— 三条缺一，入口就是不渲染。设计侧照此执行，不另立判据。
  • 理由 1（不存在的东西不出现）：没有收款码 = 用户点进去也无法付款，渲染入口等于造一个必然失败的入口；docs/21 第四节明确要求"不存在的东西不出现"。
  • 理由 2（首页节奏零成本）：入口不渲染时页面与现状逐像素一致（见各套 ?state=noqr），不需要为"暂未开放"设计一个占位块 —— 占位块是纯装饰，且每次进首页都要解释一次。
  • 理由 3（兜底链路已经存在）：商品列表底部那行来自 GET /public/purchase-hint 的运营文案本来就写着「如需下单请联系凌云进行积分充值」—— 收款码没配时，用户仍有"找谁充值"的文字路径，不会失去可达性。
  • 代价（如实说明）：管理员若只是临时停用收款码，用户会以为平台不支持充值。建议在管理端给"充值配置里一张启用码都没有"加一条醒目提示（这属于管理端职责，不进客户端）。
  • 另一种情况要分开处理：用户已在充值页（或深链直达）时配置被清空 → 页面显示空态「暂未配置收款码」+ 提交置灰，并指向「我的 › 联系客服」的纯文字（不放客服按钮，避免与我的页那个入口形成"同一入口两处出现"）。见 ?state=noconfig。

9审批要点

推荐入口：A 套（三宫格扩成四宫格）

  • 规则风险为零：「同一入口只出现一次」—— 充值全 App 只此一处，「我的」页零改动（不放任何充值按钮）。
  • 首屏成本 0dp：格数从 3 变 4 不改变行高，实测「选择分部」首卡 Y 位移 = 0，首屏可见分部卡数量不变。
  • 改动最小、可回滚：与既有工具行完全同构（同容器 / 同格宽 / 同图标尺寸 / 同字重），既有三格的顺序、图标、间距一字不改；不想要了删一行即可。
  • 未配置收款码的成本最低：同一条 Row 少画一格，没有"空条"要处理。
  • 代价与解：语义混排（售后 → 自助服务），靠"充值居末位 + 全页不出现任何'售后'字样的自称"化解。

推荐充值页形态：形态 1（档位网格 + 底部收款码卡）

与"先定金额、再付款"的心智顺序一致，未选金额时不给码（杜绝"先扫码再想金额"）；与 A/D 天然搭配。审核压力大或投诉多时，切形态 3 两步式（每屏只问一件事，越界/上限都在提交前拦住）。

待负责人拍板（4 条）

  • 入口最终位置：推荐 A（四宫格第 4 格，充值居末位）。若要求"一眼可见 + 带一句口径"，则选 C，但需同时裁两件事（通栏 vs 宣传图的先后、条上要不要带余额）。
  • 余额展示口径：推荐"服务页入口不带任何余额数字"，余额只在「我的」页积分卡 + 「我的 › 我的积分」（流水）。理由：同一个数字两处显示、两套刷新时机，迟早出现不一致。
  • 底部一行小字：建议随本次改为「先服务后结算 · 不满意可申诉 · 充值需人工审核后发放」（现状「积分由平台发放」在有了充值之后口径不完整）。「我的」页那句「积分由管理员发放 · 仅用于平台下单」不需要改 —— 充值的积分同样是管理员手工发放，语义仍然成立。
  • 换算取整口径：结构规则 12 定的是 floor（向下取整），而 core 已落地的 RechargeRules.previewPoints 用的是 round() —— 非整十比例下客户端预览会比服务端多 ≤1 积分。建议 core 改 floor，或明确"预览值可能高 1"（本稿已避开：自定义金额取 88.5 → 885，整十比例不触发分歧）。
  • 后端 400 上限文案：需中文、可直接展示（客户端原样透传）。
